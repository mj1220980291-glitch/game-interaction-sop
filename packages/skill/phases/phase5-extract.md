# Phase 5 — 模式库提取与维护（Extract）

## 定位

Phase 5 负责把项目已有的交互文档资产**提炼为可检索的模式库**，并在每次新需求完成后**按风险分级维护库**。

Phase 5 有两种场景：

| 场景 | 触发 | 目标 |
|---|---|---|
| **冷启动** | 用户显式触发，或首次启用 SOP 时隐式提议 | 从 N 个历史交互文档批量提取模式库 |
| **增量维护** | 默认每次 Phase 4 完成后自动触发 | 维护已有模式库，补充新案例/偏离/模式 |

---

## 触发条件

### 冷启动触发

**显式触发**：用户说"扫文档建库" / "导入历史" / "批量提取" / "把以前的交互文档变成模式"

**隐式触发**（用户首次使用 SOP）：
- `index.md` 不存在 **且** `docs_archive` 路径下有 ≥3 个文档
- Agent 在 Phase 1 第一回合输出前提议：
  > "看到你有 N 个历史交互文档，要先建模式库吗？建好后下次做需求就能自动复用。跳过也完全没问题，随时都能建。"
- 用户跳过 → 静默，下次仍提议（不无限追问）

### 增量维护触发

- 默认：每次 Phase 4 完成后，Agent 自动执行增量维护（按分级规则处理）
- 用户可随时说"更新模式库" / "这次有可以加进库的吗" 手动触发

---

## 场景 A：冷启动流程（5 步）

### Step 1 — 摸底清单

```
Agent 行为：
  扫 docs_archive 路径，列出所有候选文档
  按一级目录或文件名初步分类

输出格式：
  本次发现 N 个候选文档：
  
  [战斗内]（5 个）
  - 部从卡牌TIPS 战斗交互
  - MVP 展示
  - ...
  
  [局外系统]（3 个）
  - 仓库系统
  - ...
  
  [独立 / 难分类]（2 个）
  - 选秀环节预案（可能一次性）
  - ...
  
  你想：
  A. 全部都过一遍（推荐，第一次建库）
  B. 只先处理某几类
  C. 先排除已知一次性需求后再开始

注意：Agent 不自动跳过任何文档。可以提"X 看起来是一次性需求"，但最终排除需用户决定。
```

### Step 2 — 初读 + 单文档摘要（分批，每批 5 个）

```
Agent 行为：
  对每个候选文档读 H1 + 设计总览段（前 500 字以内）
  提取：触发模式 / UI 形态 / 核心交互单元 / 项目术语
  给出初判：可能模式 / 一次性需求 / 不确定

每批 5 个，输出后等用户 review：

  ── 第 1 批（5/N）──
  
  1. 部从卡牌TIPS 战斗交互
     触发：点击 / hover
     形态：右侧固定面板 + 二级浮层
     核心：选中查看详情
     术语：部从、TIPS
     初判：可能模式 ✓
  
  2. MVP 展示
     触发：战斗结束自动
     形态：全屏阻断展示
     核心：仪式感高光
     术语：MVP、部从
     初判：可能模式 ✓
  
  3. 选秀环节
     触发：系统阶段开始
     形态：专属选秀 UI
     核心：轮流选择角色
     术语：选秀、候选
     初判：一次性需求（专属界面，不太会复用）
  
  这批我标了 2 个"可能模式"、1 个"一次性"。
  你认可这批的初判吗？继续下一批？
```

**用户可修改初判**；确认后再继续下一批。

### Step 3 — 聚类草案 + 用户 review

```
所有批次初读完成后，Agent 对"可能模式"做聚类：

输出格式：
  聚类草案：
  
  Cluster 1: 战斗内选中查看详情
    候选文档：
    - 部从卡牌TIPS 战斗交互（基底）
    - 战场阶段天书查看（参考）
    共同骨架：选中 → 固定面板 → hover 子区弹二级浮层
    差异：天书没有出售按钮、信息密度不同
    建议：合并为 1 个模式 P-001
  
  Cluster 2: 全屏强制高光
    候选文档：
    - MVP 展示（基底）
    - 半决赛全使君展示（参考）
    共同骨架：全屏阻断 → 不可跳过 → 强制时长
    差异：MVP 是结算后触发、全使君是阶段开始触发
    建议：合并为 1 个模式 P-002
  
  独立（不入库）：
  - 选秀环节（已确认一次性）
  - 决赛圈展示（与 P-002 相似但差异较大，待你确认：合并 / 独立建模式 / 不入库）
  
  请审核：
  A. 哪些聚类合理？要拆 / 要合？
  B. "决赛圈展示" 你的判断？
  C. 有没有遗漏（某些独立文档应归入某聚类）？

注意：聚类通过用户 review 才写盘，不自动执行。
```

### Step 4 — 单条模式提取 + 用户 review

```
用户确认聚类后，Agent 逐条（或 2-3 条/批）提取：

Agent 行为：
  - 读基底文档 + 参考文档
  - 按 pattern-schema.md 填写 frontmatter 全字段
  - 写"核心交互逻辑"（从基底原文口语化重写，按时间序）
  - 从基底+参考的"共同点"提"必复用核心骨架"
  - 从基底+参考的"差异点"提"通常需要重定的参数"
  - 从差异点推断"容易需要重新决策的地方"
  - 写"案例对照"（基底 + 参考各一行摘要）

单案例模式（case_files 只有 1 条）：
  骨架字段标注"基于单一案例，待积累后稳定"
  这是合法的"种子模式"

输出草案后：
  "这是 P-001 的草案。要看完整内容 / 直接通过 / 修改哪里？"
  用户通过 → 落盘
  用户局部改 → 修订对应段
  用户否决 → 该模式不立（可能聚类有误，回 Step 3）
```

### Step 5 — 落盘 + 索引更新

```
所有模式 review 通过后：
  - 写入 .interaction-sop/patterns/P-XXX.md
  - 更新 .interaction-sop/index.md（模式总览表 + glossary）
  - 写 maintenance.log 记录本次建库操作
  
  输出报告：
    本次冷启动建库完成：
    - 新建 N 条模式
    - 涉及案例文件 M 个
    - 跳过 K 个一次性需求
    - Glossary 收录 J 个项目术语
    - 有 L 个模糊项记入 maintenance-suggestions.md
```

### 冷启动暂停处理

用户中途说"今天先到这里"：
- 已 review 通过的部分按正常落盘，未完成的批次丢弃
- **不持久化进度**（无跨会话进度状态）
- 下次用户重新触发时：Agent 重扫 docs_archive，发现已建模式 → 自动在 Step 3 聚类时跳过已建模式对应的文档
- Agent 提示："你已有 N 条模式，还剩 M 个文档未处理，继续吗？"

## 场景 B：增量维护（6 路决策）

Phase 4 完成后，Agent 扫本次需求与库的关系，做 6 路判断：

### 路径 1：全新需求，无命中模式

```
Agent 判断：本次需求未采用任何已有模式

Agent 问：
  "这次需求的交互模式以后可能在其他场景复用吗？
   如果会，我立一条新模式。"

用户说"会" → 进入"立新模式"小流程（见分级表 Row 3）
用户说"不会" → 跳过，不维护库
```

### 路径 2：完整采用 P-XXX，无偏离

```
Agent 自动：
  把本次交互文档追加到 P-XXX 的 case_files
  更新 last_reviewed_at
  写 maintenance.log
  输出："P-XXX 案例 +1（[文档名]）"
```

### 路径 3：采用 P-XXX，有偏离

```
Agent 输出：
  "这次有 N 条偏离 P-XXX。
   我来分一下：
   - DEV-A（[内容]）：看起来是场景特定的一次性偏离
   - DEV-B（[内容]）：可能会在同类场景里反复出现
   
   你想把哪些写进 deviations.md？"

Agent 按用户选择，把确认的偏离写入 deviations.md，写 maintenance.log
```

### 路径 4：采用 P-XXX，但偏离非常多（≥ 3 条）

```
Agent 输出：
  "这次偏离 P-XXX 的程度比较高，有 N 条偏离。
   有两个选项：
   A. 立一个新模式（P-YYY），保留 P-XXX 不变
   B. 把 P-XXX 拆分成 P-XXXa + P-XXXb 两个变体
   C. 先都记成偏离，后续看情况
   
   你倾向哪个？"

A / B → 写 maintenance-suggestions.md（结构性变更，不自动执行）
C → 写偏离记录
```

### 路径 5：未命中模式，但完成后发现与某模式高度相似

```
Agent 在 Phase 4 完成后扫库发现：
  "这次实际产出的逻辑和 P-XXX 很像，但 Phase 0 没命中。
   可能是 matching_signals 需要补充。
   要在 P-XXX 里补几个 intent/ui 信号吗？"

用户同意 → 自动更新 matching_signals，写 maintenance.log
用户拒绝 → 跳过
```

### 路径 6：同时采用多个模式 + 大量业务专属决策

```
Agent 输出：
  "这次同时用了 P-XXX 和 P-YYY，还有 N 条业务专属决策（超出两个模式的覆盖范围）。
   这 N 条独有逻辑以后会在其他场景复用吗？
   会的话我建议立一个新模式 P-ZZZ。"

用户说"会" → 立新模式（见分级表 Row 3）
用户说"不会" → 跳过
```

## 增量操作分级表

| 级别 | 操作类型 | 处理方式 |
|---|---|---|
| 低风险（数据追加型） | case_files 追加 / last_reviewed_at 更新 / glossary 同义词补充 / 一次性偏离追加 | **全自动** + maintenance.log |
| 低中风险（元数据修订型） | matching_signals 补充 / 项目术语别名更新 | **全自动** + maintenance.log |
| 中风险（立新模式） | 创建新 P-XXX | 草案**直接落盘** + 一句话提示 + 用户随时一句话推翻 |
| 高风险（结构性变更） | 拆分 / 合并 / 废弃 / 修改核心骨架字段 | 写 `maintenance-suggestions.md`，**禁止自动执行**，必须用户 review |

---

## 9 条硬规则

**R-Extract-1**：`case_files` 必须 ≥1。没有真实案例文档支撑的模式禁止写入。

**R-Extract-2**：冷启动时，"必复用核心骨架"必须基于 ≥2 个案例的共同点。只有 1 个案例时，骨架字段标"基于单一案例，待积累后稳定"（种子模式合法）。

**R-Extract-3**：不允许"凭空造规则"——模式里每条规则必须能在 case_files 指向的文档中找到对应描述或隐含逻辑，不能是 Agent 凭空想象的"应该有这个规则"。

**R-Extract-4**：`matching_signals.anti_signals` 必填。从聚类阶段"未入此模式的相似文档"反推；不允许留空数组。

**R-Extract-5**：增量维护写盘操作必须写 maintenance.log。操作类型、目标 ID、关键参数三项缺一不可。

**R-Extract-6**：增量 Phase 4 完成后触发维护时，如无任何操作需要执行（如全新一次性需求且用户明确跳过），则不向用户输出任何维护相关内容——静默结束。

**R-Extract-7**：偏离记录的 `reason` 字段必填，禁止留空或填"待补充"。写入前 Agent 必须确认 reason 已获得用户明确说明。

**R-Extract-8**：结构性变更（拆分 / 合并 / 废弃 / 修改核心骨架）禁止自动执行。只能写入 maintenance-suggestions.md，等用户下次启动 SOP 时审批。

**R-Extract-9**：冷启动期间任何写盘操作 SHALL 在用户 review 通过该条目后才执行，不可批量预写盘。

## Glossary 自动维护

Agent 在 Phase 5 提取或增量维护时，对每条新模式执行 glossary 维护：

1. 扫新模式的 `project_terms` 字段
2. 与 `index.md` 中 `project_glossary` 比对：
   - **新词**：自动追加 `{ term: X, aliases: [], first_seen: P-YYY }`
   - **可能的别名**（语义判断相同概念）：写入 `maintenance-suggestions.md` 提议合并，不自动修改
3. 写 maintenance.log 记录 glossary 变更

---

## 用户 Override 能力

用户可随时通过自然语言执行以下操作，Agent 识别意图后立即执行：

| 用户说 | Agent 行为 |
|---|---|
| "停掉自动维护" / "以后都问我" | 在 `index.md` frontmatter 追加 `auto_mode: review_all`，后续所有增量操作改为询问 |
| "P-XXX 直接删掉" | 删除 `patterns/P-XXX.md`，更新 `index.md` 总览表，写 maintenance.log |
| "把上周 / 昨天的自动操作撤销" | 解析 maintenance.log 匹配时间窗口，按倒序执行回滚，log 末尾记录回滚动作 |
| "P-XXX 不要再自动加 case 了" | 在 `P-XXX.md` frontmatter 设置 `auto_maintain: false`，后续相关增量改为询问 |
| "继续建库" / "继续扫文档" | 重新触发冷启动，自动跳过已建模式对应的文档 |

---

## 失败回退

| 情况 | 处理 |
|---|---|
| 用户中途说"算了，先不建库" | 已 review 通过的部分落盘，未完成批次丢弃 |
| 用户说"全都不要" | 不写任何文件，回到原 SOP |
| 写盘失败（文件权限等） | 报错，暂停，等用户处理后重试 |
| 模式草案被用户反复否决 | 第 3 次否决时 Agent 询问："要不要从聚类阶段重新梳理，还是直接跳过这个？" |
