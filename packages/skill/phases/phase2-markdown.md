# Phase 2 — v2 Markdown 生成

## 进入条件

Phase 1 已达到`信息可用`或`信息充分`。

## 完成条件

- 完整 v2 Markdown 已在对话中输出，用户确认无误
- Markdown 通过 `references/markdown-v2-spec.md` 全部强校验
- 文件已保存到磁盘

---

## Step 0 — 分类决策（写 Markdown 前必经路径）

> **重要**：Step 0 是 Phase 2 的 hard gate。跳过 Step 0 直接写 Markdown，章节/簇分类几乎必然按"流程时段"或"动作过程"切，而不是按"界面 / 功能模块"切，下游会被引擎的 `H_SECTION_NOT_INTERFACE` 硬错与 `W_CLUSTER_NAME_LOOKS_RULE` 软警告反复打脸。

LLM 输出完整 Markdown **之前**，依次完成下列 4 个子步骤，每步以用户确认作为通过门。

### Step 0.1 — 列界面 / 场景态清单（锚定图）

LLM 列出本需求涉及的"界面 / 场景态"清单。**每一项必须锚定一张可截图的界面态**：

- **路径A（入场时已有图）**：清单直接来自用户提供的草稿 / 截图 / 设计稿——一图一章
- **路径B（AI 已画草稿并经用户确认）**：清单来自已确认的草稿图
- **无任何图可依时**（用户拒绝画草稿）：每项附一句"这张图上应能看到什么"的文字速写，供用户脑补确认

> **禁止按业务流程切章**。章节名描述的是"玩家在哪个画面"，不是"玩法进行到哪个环节"。簇的归属由"控件出现在哪张图上"决定，不由业务流程决定（详见 `markdown-v2-spec.md` 转写文体规范与下方 Step 0.2）。

输出格式：

```
本需求涉及的界面清单（草案，每项 = 一张可截图的界面态）：

1. [界面名] — [一句功能定位]〔锚定：图N / 文字速写：这张图上应能看到…〕
2. [界面名] — [一句功能定位]〔锚定：…〕
…

涉及多态时显式标注：
  - 态1 vs 态2 的功能模块差异 ≈ N 个
  - 决策：拆 N 个界面 / 合 1 个界面（理由：依据多态拆分指南）

请审核：清单是否覆盖？每张图对应一个界面态吗？要补充 / 调整哪些？
```

**多态拆分判断（参考 markdown-v2-spec.md 多态拆分指南）**：
- 两态之间**功能模块差异 ≥ 2-3 个**（新增/移除/重命名的可识别信息块）→ 拆 N 个章节
- 否则 → 合 1 个章节，态差异用簇 / 子分类 / 对比图表达

> **流程型策划稿特别提醒**：策划稿常按玩法流程分节（如"抓捕流程：开火→包裹→挣脱→押送"）。**不要照搬流程章**——按界面态重切。例：策划稿的"逮捕按钮"若实际弹出在"警察身份领取"界面态的图上，则它归该界面态章节，而非另立"抓捕流程"章；环节里在某张图上找不到可指认控件的规则（如"押送解除条件由服务端控制"）走 Step 0.3 丢弃清单。

### Step 0.2 — 对每个界面列功能模块清单

用户确认界面清单后，LLM 对每个界面列"功能模块 / 信息块"清单。**模块限定为：该图上玩家能用气泡指认的东西**——图上指不到的（纯服务端逻辑、纯演出）不进清单，走 Step 0.3 丢弃。

```
界面 1：[界面名]（锚定：图N）
  - [该图上可指认的模块/信息块名词]
  - [该图上可指认的模块/信息块名词]
  …

界面 2：[界面名]
  - …

请审核：每个界面下的模块拆分是否准确？模块名应是该图上玩家能用气泡指认的东西。
```

**功能模块的判断标准**：
- 玩家站在该界面前**能用一个名词指认、且能在图上指气泡**（"血量条" / "锁定按钮" / "基础信息区" / "属性概览"）
- 而不是程序流程动作（"传送" / "下发" / "结算返回"）
- 也不是规则属性（"显示规则" / "动效时机" / "异常处理"）
- 也不是图上看不见的服务端逻辑（"押送解除" / "并发裁决"）——这类走 Step 0.3 丢弃清单

**控件归属跟随主图**：同一控件归入它**实际出现的那张图**对应的章节，而非它所属的业务流程环节。例："逮捕按钮"按流程属抓捕环节，但实际弹出在身份领取界面态的图上 → 归该界面态章节的模块清单。

> **小需求合并提示**：若需求规模小（涉及界面 ≤ 2 个），可把 0.1 与 0.2 合并到一轮输出，但仍保留两段清单的结构化区分。

### Step 0.3 — 规则归位 + 显式丢弃清单（三分法）

LLM 拿策划稿**每条**规则做三分法处理。**目标不是穷尽收录，而是"该进簇的进簇、图上不可见的显式丢弃"**：

```
规则归位（草案）：

✓ 规则 1（策划稿原文摘要）→ 界面 N . 模块 M
✓ 规则 2 → 界面 N . 模块 M
…

✗ 规则 X → 丢弃（理由：[四类判据之一]）
✗ 规则 Y → 丢弃（理由：[四类判据之一]）
…

⚠ 规则 Z → 无法判断（疑似漏界面 / 漏模块 / 跨界面全局规则，需用户确认）
…

请审核：
- ✓ 归位是否合理？
- ✗ 丢弃清单是否认可？（可推翻任意一条，让它回到 ✓ 或 ⚠）
- ⚠ 无法判断的规则需要补哪个界面/模块，或确认是跨界面规则？
```

**四类丢弃判据**（详见 `markdown-v2-spec.md` T2）：

1. **纯服务端规则且无 UI 表现**——持续时间 / 解除条件 / 并发裁决等由服务端控制、界面仅同步结果（如"泡泡持续时间由服务端控制""押送解除条件由服务端控制"）
2. **纯环境演出**——无控件可指的演出（如"高度到 400 米天空盒切换为宇宙星空""落地触发烟花特效"且图上无对应控件）
3. **预留不开发的交互**（如"点按方向键只位移不转朝向为预留交互，本版本不开发"）
4. **开关 / 状态的反面显然陈述**——与正面陈述互为镜像（如已写"开启时自动铺底色"，则"关闭时不铺底色"丢弃）

> **丢弃 SHALL NOT 静默执行**。每条丢弃必须列出理由交用户确认，用户可推翻。这与"穷尽归位每条规则"是相反的导向——旧做法会把服务端规则、纯演出硬塞进簇，导致设计师终稿大量删除。

**小需求可省略独立轮次**：策划稿规则 < 10 条且 0.2 输出已显然覆盖时，可把 0.3 合并到 0.2 的同一轮回复中（用 "（同时给出归位与丢弃清单如下）" 衔接），但三分法结构（✓/✗/⚠）仍需保留。

### Step 0.4 — 终态确认

用户对完整分类决策给出 OK：

```
最终分类决策：

- 界面清单（每项锚定一张可截图的界面态）：✓
- 各界面的模块清单（该图上可指认控件）：✓
- 规则归位（✓ 进簇）：✓
- 丢弃清单（✗ 不进簇，含理由，已确认）：✓
- 无法判断项（⚠）处理：✓

⇒ ## NN. 章节名 = 上述每个"界面"名（按 INTERFACE_KEYWORDS 命名 ✓）
⇒ ### 簇名 = 该章节对应界面下的"模块/信息块"名（名词性 ✓）
⇒ 丢弃的规则不进任何簇

确认无误后，我将基于此决策写完整 Markdown。
```

用户回复 "确认 / 开始写" → 进入"第一步：在对话里输出完整 Markdown"。

### 用户跳过 Step 0 时

若用户说"直接给我写完整 markdown" / "不用问那么多" 等：

LLM **不应** 直接跳过 Step 0，而是简短说明：

> "按 SOP 流程需要先做 4 步分类决策，否则章节/簇分类几乎必然偏差。我先把界面清单 0.1 给你，你看一眼就行（< 30 秒），不用 4 轮都仔细审。"

仍输出 Step 0.1。极端情况下用户坚持跳过，照写 Markdown，但需在自检清单标注 "Step 0 user-skipped"，由用户在审核时承担分类风险。

## 第一步：在对话里输出完整 Markdown

Step 0 通过后，按 `references/markdown-v2-spec.md` 模板写出完整 Markdown，**不省略任何章节**。

输出前自检：

- [ ] **0.1 界面/场景态清单已与用户确认（每项锚定一张可截图的界面态，无流程章）**
- [ ] **0.2 每个界面的功能模块清单已与用户确认（模块 = 该图上可指认控件）**
- [ ] **0.3 策划稿每条规则已归位（✓）或列入丢弃清单（✗，含理由并经用户确认）；无法判断项（⚠）已处理**
- [ ] **0.4 完整分类决策（界面 ↔ 章节, 模块 ↔ 簇, 丢弃清单）已与用户确认**
- [ ] **文档内无"待确认 / 待拍板 / 待策划确认"类行内标记**（出现 = Phase 1 冲突清零门禁被绕过 → 回退 Phase 1 拍板该冲突后重写该段，不保留标记）
- [ ] 文件头 4 行齐全（跟进UI / 需求组 / 易协作链接 / 最后更新时间）
- [ ] 一级标题只有 `# [需求名称]` 一个
- [ ] `## 设计总览` 唯一存在
- [ ] 设计总览下正好 `### 功能背景` + `### 核心交互` 两块，无其他三级标题
- [ ] 至少 1 个 `## NN. [界面名称]`
- [ ] `##` 序号连续：`01, 02, 03, ...`
- [ ] **【S3 硬规则】每个 `## NN.` 章节名含界面关键词清单（界面/面板/页/窗/卡/弹窗/弹层/区/条/栏/区域/版/入口/反馈/场景）OR 在全局规范白名单（全局/规范/组件/汇总/流程/结算）**
- [ ] 每个 `## NN.` 至少 1 个 `###`
- [ ] 设计总览以外的每个 `###` 下方第一行是 `@角色...`
- [ ] 角色名单只用：`@程序 @GUI @拼接 @美术 @动效 @音频 @策划`（详见 `../references/role-tags.md`）
- [ ] **【W6 软警告】`###` / `####` 命名 = 界面上可识别的功能模块/信息块名词（如"基础信息"、"出售按钮"、"hover 触发区"）；行为单元可用 `xxx 行为` / `xxx 流程`；禁止以规则属性后缀结尾（时机/规则/层级/限制/边界/兼容/表现）**
- [ ] **【W2 软警告】`###` / `####` 不准用死分类词（显示规则/操作规则/反馈表现/异常与边界/功能定位/配图说明/注意事项）**
- [ ] 每个 `###` 对应该主图上一个能独立指气泡的可见控件（丢弃清单里的内容不在其中）
- [ ] 同一功能涉及的所有规则（显示/状态/动效/异常/网络）都聚集在该功能的 `###` 内，不被拆到多个 `###`
- [ ] 【C3 硬规则】一个视觉单元的所有状态/hover/态切换规则必须聚在同一个 `###`，禁止拆成"默认态 ###" + "hover态 ###"
- [ ] 【T3】同一控件的规则跨簇归位合并到一个簇，不按策划稿段落结构分裂
- [ ] 【T4】控件名/状态名跟随设计稿实际文案（治安官 ≠ 警官蛋；按钮 ≠ pill）
- [ ] 【T5】每个控件簇自问"有无可见反馈"，策划稿未写时按常识补一条（toast/浮显/高亮/音效），正常陈述、不加待确认
- [ ] 【W4】bullet 粒度 = 完整行为叙述（同控件常规规则合并成一条，强调/风险点独立成条），非原子化拆分
- [ ] 【T6】无复述设计稿可见信息、无穷举范围声明、无占位物描述；参数清单已收束为"策划配表即可"
- [ ] 【T6】每簇 bullet 数（不含配图）3–6 条；超过 6 条已先删减合并，再考虑 `####`
- [ ] 【T7】同簇无同义重复 bullet（含状态行与普通规则重复）
- [ ] 【T8】动效 bullet 直接写一句"什么情况下，需要什么样的动效"——不加"动效需求："前缀、不用冒号；先情况后动效，后半句写清谁动、怎么变、什么节奏；同类动效已合并；有显隐的 UI 覆盖出现与隐藏；无"形式待定 / 节奏由策划配置"空句
- [ ] 【T9】每簇按"是什么 → 怎么交互 → 有哪些状态 → 反馈"顺序书写；状态行连续；动效句在簇末
- [ ] 【状态行】写作"xx状态：出现条件"或只写"xx状态"；冒号后不写外观、不写动效（动效另起一条动效句）；无 `状态·` 前缀
- [ ] 【W3】配图 bullet 紧跟它所说明的规则；状态类簇一态一图
- [ ] 【可选】按 T6 / T7 / T8 删减合并后，一个 `###` 下 bullets 仍 > 6 条且能分类时，才用 `#### 子分类标题` 做内部分组（例如"基础信息" / "升级反馈"），详见 `markdown-v2-spec.md` 的"簇内子分类小标题"章节

## 章节内 `###` 拆分启发法（写 Markdown 时用）

> **基本原则**：`###` 簇名 = 该章节对应界面上玩家可识别的"功能模块 / 信息块"名词；行为单元可用 `xxx 行为` / `xxx 流程` 替代名词。**禁止**用动作过程动词短语（如"触发与传送" / "候选下发" / "结算返回"）。

对每个 `## NN. [界面名称]`：

1. 把该界面相关的所有规则/决策列出来（从 Step 0.3 归位映射直接拿）
2. 按"界面上能用一个名词指认的东西" 把规则分组——一个模块 = 一组规则 = 1 个 `###`
3. `###` 名字用该模块的**名词**命名：
   - ✅ **正例**：基础信息 / 锁定按钮 / hover 触发区 / 卡片列表 / 顶部信息条 / 属性概览 / 出售按钮 / 等级徽章
   - ✅ **行为单元正例**（找不到 UI 名词时）：折叠行为 / hover 行为 / 触发流程 / 切换流程
   - ❌ **反例（动作过程）**：触发与传送 / 候选下发 / 二选一交互 / 结算返回 / 抢夺与并发仲裁 / 揭示与公共池过场
   - ❌ **反例（规则属性后缀，触发 W6）**：展开收起时机 / 显示位置与层级 / 阶段限制与强制收起 / 视觉层级与遮挡
   - ❌ **反例（死分类，触发 W2）**：显示规则 / 操作规则 / 反馈表现 / 异常与边界 / 功能定位 / 注意事项 / 配图说明
4. `###` 下方写 `@角色1 @角色2 ...`，列出该组规则真正涉及的角色
5. 组内规则按 bullet 列出（按 T6 只写图上看不出来的信息增量，目标 3–6 条；按 T9 顺序：是什么 → 怎么交互 → 有哪些状态 → 反馈；状态按 T10 写成"xx状态：出现条件"；动效按 T8 直接写"什么情况下，需要什么样的动效"（无前缀）并放在簇末）
6. 判断哪些规则需要配图（见下方规则），需要则在**该条规则紧后**插一条 `- 配图：[具体说明]`；一簇可多张

**配图判断规则（何时加 `配图：` bullet）：**

> **位置即语义**：`配图：` 紧跟它所说明的那条规则，不归拢到簇末。有多条状态行的簇优先一态一图——每条状态行后各跟一条 `配图：`。

以下情况**应加**配图 bullet：
- 该簇有**主图上未覆盖的状态**（主图只截一个时间点，该簇描述的另一个状态需要单独补图）
- 该簇描述的状态虽然主图有，但**需要单独强调**（如关键交互节点、UI 对比、弹层叠加关系）
- 该簇涉及**局部细节**：卡片内部布局、小 icon/徽章/角标、悬浮层位置、角色标签排布等，主图分辨率不够清楚
- 该簇描述**多个并排状态**（如"选中态 vs 未选中态"、"激活 vs 锁定"）需要对比图

以下情况**不加**配图 bullet：
- 主图已完全覆盖该状态，无额外信息需要传达
- 纯规则 / 逻辑说明（如"倒计时结束自动锁定"），无需截图

`配图：` 后接**给设计师看的一句话说明**，说清楚"截什么"：

## 常见错误风格 → 修正方向对照

| 错误风格 | 修正方向 |
