# Phase 2 — v2 Markdown 生成

## 进入条件

Phase 1 已达到`信息可用`或`信息充分`。

## 完成条件

- 完整 v2 Markdown 已在对话中输出，用户确认无误
- Markdown 通过 `references/markdown-v2-spec.md` 全部强校验
- 文件已保存到磁盘

---

## Step 0 — 分类决策（写 Markdown 前必经路径）

> **重要**：Step 0 是 Phase 2 的 hard gate。跳过 Step 0 直接写 Markdown，章节/簇分类几乎必然按"流程时段"或"动作过程"切，而不是按"界面 / 功能模块"切，下游会被引擎的 `H_SECTION_NOT_INTERFACE` 硬错与 `W_CLUSTER_NAME_LOOKS_RULE` 软警告反复打脸。

LLM 输出完整 Markdown **之前**，依次完成下列 4 个子步骤，每步以用户确认作为通过门。

### Step 0.1 — 列界面 / 场景态清单

LLM 列出本需求涉及的"界面 / 场景态"清单，每项含一句功能定位。输出格式：

```
本需求涉及的界面清单（草案）：

1. [界面名] — [一句功能定位]
2. [界面名] — [一句功能定位]
…

涉及多态时显式标注：
  - 态1 vs 态2 的功能模块差异 ≈ N 个
  - 决策：拆 N 个界面 / 合 1 个界面（理由：依据多态拆分指南）

请审核：清单是否覆盖？要补充 / 调整哪些？
```

**多态拆分判断（参考 markdown-v2-spec.md 多态拆分指南）**：
- 两态之间**功能模块差异 ≥ 2-3 个**（新增/移除/重命名的可识别信息块）→ 拆 N 个章节
- 否则 → 合 1 个章节，态差异用簇 / 子分类 / 对比图表达

### Step 0.2 — 对每个界面列功能模块清单

用户确认界面清单后，LLM 对每个界面列"功能模块 / 信息块"清单：

```
界面 1：[界面名]
  - [模块/信息块名词]
  - [模块/信息块名词]
  …

界面 2：[界面名]
  - …

请审核：每个界面下的模块拆分是否准确？模块名应是该界面上玩家能识别的东西。
```

**功能模块的判断标准**：
- 玩家站在该界面前能用一个名词指认（"血量条" / "锁定按钮" / "基础信息区" / "属性概览"）
- 而不是程序流程动作（"传送" / "下发" / "结算返回"）
- 也不是规则属性（"显示规则" / "动效时机" / "异常处理"）

> **小需求合并提示**：若需求规模小（涉及界面 ≤ 2 个），可把 0.1 与 0.2 合并到一轮输出，但仍保留两段清单的结构化区分。

### Step 0.3 — 规则归位映射

LLM 拿策划稿每条规则尝试归位到 (界面, 模块) 二元组：

```
规则归位（草案）：

规则 1（策划稿原文摘要）→ 界面 N . 模块 M
规则 2 → 界面 N . 模块 M
…

⚠️ 无法归位的规则：
- 规则 X：[原因——疑似漏界面 / 漏模块 / 跨界面全局规则]
- 规则 Y：[原因]

请审核：归位是否合理？⚠️ 标记的规则需要补哪个界面/模块，或确认是跨界面规则？
```

**小需求可省略**：策划稿规则 < 10 条且 0.2 输出已显然覆盖所有规则时，可把 0.3 合并到 0.2 的同一轮回复中（用 "（同时给出归位映射如下）" 衔接）。

### Step 0.4 — 终态确认

用户对完整分类决策给出 OK：

```
最终分类决策：

- 界面清单：✓
- 各界面的模块清单：✓
- 规则归位（含 flag 处理）：✓

⇒ ## NN. 章节名 = 上述每个"界面"名（按 INTERFACE_KEYWORDS 命名 ✓）
⇒ ### 簇名 = 该章节对应界面下的"模块/信息块"名（名词性 ✓）

确认无误后，我将基于此决策写完整 Markdown。
```

用户回复 "确认 / 开始写" → 进入"第一步：在对话里输出完整 Markdown"。

### 用户跳过 Step 0 时

若用户说"直接给我写完整 markdown" / "不用问那么多" 等：

LLM **不应** 直接跳过 Step 0，而是简短说明：

> "按 SOP 流程需要先做 4 步分类决策，否则章节/簇分类几乎必然偏差。我先把界面清单 0.1 给你，你看一眼就行（< 30 秒），不用 4 轮都仔细审。"

仍输出 Step 0.1。极端情况下用户坚持跳过，照写 Markdown，但需在自检清单标注 "Step 0 user-skipped"，由用户在审核时承担分类风险。

## 第一步：在对话里输出完整 Markdown

Step 0 通过后，按 `references/markdown-v2-spec.md` 模板写出完整 Markdown，**不省略任何章节**。

输出前自检：

- [ ] **0.1 界面/场景态清单已与用户确认**
- [ ] **0.2 每个界面的功能模块清单已与用户确认**
- [ ] **0.3 策划稿每条规则已归位（含无法归位的 flag 与处理）**
- [ ] **0.4 完整分类决策（界面 ↔ 章节, 模块 ↔ 簇）已与用户确认**
- [ ] 文件头 4 行齐全（跟进UI / 需求组 / 易协作链接 / 最后更新时间）
- [ ] 一级标题只有 `# [需求名称]` 一个
- [ ] `## 设计总览` 唯一存在
- [ ] 设计总览下正好 `### 功能背景` + `### 核心交互` 两块，无其他三级标题
- [ ] 至少 1 个 `## NN. [界面名称]`
- [ ] `##` 序号连续：`01, 02, 03, ...`
- [ ] **【S3 硬规则】每个 `## NN.` 章节名含界面关键词清单（界面/面板/页/窗/卡/弹窗/弹层/区/条/栏/区域/版/入口/反馈/场景）OR 在全局规范白名单（全局/规范/组件/汇总/流程/结算）**
- [ ] 每个 `## NN.` 至少 1 个 `###`
- [ ] 设计总览以外的每个 `###` 下方第一行是 `@角色...`
- [ ] 角色名单只用：`@程序 @GUI @拼接 @美术 @动效 @音频 @策划`（详见 `../references/role-tags.md`）
- [ ] **【W6 软警告】`###` / `####` 命名 = 界面上可识别的功能模块/信息块名词（如"基础信息"、"出售按钮"、"hover 触发区"）；行为单元可用 `xxx 行为` / `xxx 流程`；禁止以规则属性后缀结尾（时机/规则/层级/限制/边界/兼容/表现）**
- [ ] **【W2 软警告】`###` / `####` 不准用死分类词（显示规则/操作规则/反馈表现/异常与边界/功能定位/配图说明/注意事项）**
- [ ] 每个 `###` 数量符合"主图上能独立指气泡的看得见的东西"数量，等于策划文档原标号数
- [ ] 同一功能涉及的所有规则（显示/状态/动效/异常/网络）都聚集在该功能的 `###` 内，不被拆到多个 `###`
- [ ] 【C3 硬规则】一个视觉单元的所有状态/hover/态切换规则必须聚在同一个 `###`，禁止拆成"默认态 ###" + "hover态 ###"
- [ ] bullet 原子化（一条规则 = 一个条件 + 一个行为 + 一个结果）
- [ ] 【可选】一个 `###` 下 bullets ≥ 6 条且能分类时，考虑用 `#### 子分类标题` 做内部分组（例如"基础信息" / "升级反馈"），详见 `markdown-v2-spec.md` 的"簇内子分类小标题"章节

## 第二步：请用户审核

在 Markdown 后面附上简短的请求：

```
请审核上面这份 Markdown：
- 字段是否准确？
- 章节/簇切分是否与 Step 0 决策一致？
- 任何一条规则需要修改/补充？

确认无误后我保存到磁盘。
```

如果用户提修改，按修改重写完整 Markdown，再次请求确认。**不要发"差异 patch"，每次都重发完整版**——便于用户复制到自己的工具。

## 章节内 `###` 拆分启发法（写 Markdown 时用）

> **基本原则**：`###` 簇名 = 该章节对应界面上玩家可识别的"功能模块 / 信息块"名词；行为单元可用 `xxx 行为` / `xxx 流程` 替代名词。**禁止**用动作过程动词短语（如"触发与传送" / "候选下发" / "结算返回"）。

对每个 `## NN. [界面名称]`：

1. 把该界面相关的所有规则/决策列出来（从 Step 0.3 归位映射直接拿）
2. 按"界面上能用一个名词指认的东西" 把规则分组——一个模块 = 一组规则 = 1 个 `###`
3. `###` 名字用该模块的**名词**命名：
   - ✅ **正例**：基础信息 / 锁定按钮 / hover 触发区 / 卡片列表 / 顶部信息条 / 属性概览 / 出售按钮 / 等级徽章
   - ✅ **行为单元正例**（找不到 UI 名词时）：折叠行为 / hover 行为 / 触发流程 / 切换流程
   - ❌ **反例（动作过程）**：触发与传送 / 候选下发 / 二选一交互 / 结算返回 / 抢夺与并发仲裁 / 揭示与公共池过场
   - ❌ **反例（规则属性后缀，触发 W6）**：展开收起时机 / 显示位置与层级 / 阶段限制与强制收起 / 视觉层级与遮挡
   - ❌ **反例（死分类，触发 W2）**：显示规则 / 操作规则 / 反馈表现 / 异常与边界 / 功能定位 / 注意事项 / 配图说明
4. `###` 下方写 `@角色1 @角色2 ...`，列出该组规则真正涉及的角色
5. 组内规则按 bullet 列出
6. 判断该簇是否需要配图（见下方规则），需要则在该簇最后加一条 `- 配图：[具体说明]`

**配图判断规则（何时加 `配图：` bullet）：**

以下情况**应加**配图 bullet：
- 该簇有**主图上未覆盖的状态**（主图只截一个时间点，该簇描述的另一个状态需要单独补图）
- 该簇描述的状态虽然主图有，但**需要单独强调**（如关键交互节点、UI 对比、弹层叠加关系）
- 该簇涉及**局部细节**：卡片内部布局、小 icon/徽章/角标、悬浮层位置、角色标签排布等，主图分辨率不够清楚
- 该簇描述**多个并排状态**（如"选中态 vs 未选中态"、"激活 vs 锁定"）需要对比图

以下情况**不加**配图 bullet：
- 主图已完全覆盖该状态，无额外信息需要传达
- 纯规则 / 逻辑说明（如"倒计时结束自动锁定"），无需截图

`配图：` 后接**给设计师看的一句话说明**，说清楚"截什么"：
```
- 配图：选中态与未选中态候选卡对比（上浮放大 vs 原大小）
- 配图：P3 阶段激活玩家的金色光圈特效与锁定态紫色禁锢特效对比
- 配图：8 张公共卡池 4+4 错位排列布局
```

## 常见错误风格 → 修正方向对照

| 错误风格 | 修正方向 |
|---|---|
| `## 01. 准备环节` | `## 01. 浮岛站位场景`（指代具体界面态）|
| `## 02. 私密选择环节` | `## 02. 私密二选一界面`（指代具体界面态）|
| `### 触发与传送`（动作） | `### 传送行为` 或并入 `### 浮岛站位` 模块的 bullet |
| `### 候选下发`（动作）| `### 候选卡区` 或 `### 卡片下发流程`（行为单元）|
| `### 显示位置与层级`（规则属性） | `### 显示位置`（去"层级"后缀）或 `### 卡片定位区` |
| `### 展开 / 收起时机`（规则属性） | `### 折叠行为`（行为单元）或并入对应 UI 元素簇 |
| `### 显示规则`（死分类）| 拆到具体功能模块簇里，或改 `### 卡片显示规则`（仍可触发，建议彻底拆）|

## 引擎反馈循环

写完 Markdown 后调用 `validate_v2_markdown` 工具自动校验，重点看：

- **errors** 中如有 `V2_H_SECTION_NOT_INTERFACE` → 必改：章节命名按 Step 0.1 重做，不要凑字过校验
- **warnings** 中如有 `V2_W_CLUSTER_NAME_LOOKS_RULE` → 应改：按上面"对照表"修正方向重命名
- **warnings** 中如有 `V2_W2_DEAD_CATEGORY_CLUSTER_NAME` → 应改：拆到具体功能模块簇
- **warnings** 中如有 `V2_W3_CLUSTER_MIXED_FREE_BULLETS_AND_GROUPS` → 可改：要么全分组、要么全不分

软警告默认不阻断保存，但用户审核时**通读所有 warning**，either 改名 or 显式确认"为什么忽略"。
