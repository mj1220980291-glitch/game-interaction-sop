# Phase 0 — 翻库咨询（Recall）

## 定位

Phase 0 是 SOP 在 Phase 1 第一回合开口前由 Agent 内部完成的**检索与对比流程**。Phase 0 不构成独立对话回合——其输出嵌入 Phase 1 第一回合，用户感受到的是"Agent 一开口就已经看过老案例"，而不是"先查查，再问你"。

**前提**：项目根存在 `.interaction-sop/index.md` 且模式总览表非空。任何一项不满足则**静默退化**为原 Phase 1。

---

## 8 步内部流程

```
[1] 启动检查
[2] 解析用户需求
[3] 候选检索
[4] 候选筛选
[5] 深入对比
[6] 评估覆盖范围
[7] 嵌入 Phase 1 第一回合输出
[8] 退化
```

---

### [1] 启动检查

检查以下条件，**任意一项不满足则跳到 [8] 退化**：

- `.interaction-sop/index.md` 文件存在
- `index.md` frontmatter 的 `schema_version` 与当前 skill 版本一致（不匹配见 [8] 退化）
- `index.md` 正文的"模式总览"表格至少有 1 行数据（status=active 的模式）

---

### [2] 解析用户需求

从用户输入的策划文档或需求描述中提取：

- **意图关键词**：用户想做什么（如"选中查看详情" / "购买" / "阶段切换"）
- **UI 信号**：可能涉及的 UI 形态（如"固定面板" / "全屏弹窗" / "列表"）

**Glossary 别名归一**：读取 `index.md` frontmatter 的 `project_glossary`，将用户描述中出现的别名归一为主术语。

例：用户说"信息卡片弹出来" → 通过 glossary 识别"信息卡片"是"TIPS"的别名 → 内部以"TIPS"参与检索。

---

### [3] 候选检索（仅读 frontmatter）

对"模式总览"表中每条 `status=active` 的模式，读取其 frontmatter（不读正文）并计算分数：

```
score = intent 命中数 + ui 命中数 - anti 命中数 × 2
```

- `intent 命中数`：用户意图关键词在 `matching_signals.intent_keywords` 中命中几个
- `ui 命中数`：UI 信号在 `matching_signals.ui_signals` 中命中几个
- `anti 命中数`：用户意图或 UI 信号在 `matching_signals.anti_signals` 中命中几个（权重 ×2，因为误配代价 > 漏配）

**阈值**：score ≥ 2 进入候选。阈值为建议值，Agent 应根据命中质量自适应判断——"把这个候选念给用户，用户是否会说'这俩没关系'"是最终判断标准。

---

### [4] 候选筛选

| 候选数 | 处理方式 |
|---|---|
| 0 | 跳到 [8] 退化 |
| 1 | 完整深入此模式 |
| 2 | 两个都深入，输出时各用简版 |
| ≥3 | 深入分数最高的 2 个；其余在输出末尾以"另外检索到 X / Y 可能相关，要展开吗？"列出 |

---

### [5] 深入对比（读正文）

对每个要深入的候选，读取完整条目正文，将模式各段与新需求做**三层标记**：

| 标记类型 | 来源段 | 用途 |
|---|---|---|
| (a) 基本可复用 | `## 必复用的核心骨架` | 用户需求无矛盾 → 直接纳入"骨架可复用"部分 |
| (b) 待你确认 | `## 通常需要按需求重定的参数` | 每次套用都要补的参数 |
| (c) 我留意到的差异 | `## 容易需要重新决策的地方` | 用这些维度扫新需求，命中的主动提示 |
| (d) ⚠️ 矛盾点 | `## 必复用的核心骨架` | **策划文档与骨架直接冲突**，必须暴露（见"⚠️ 冲突处理"段） |
| (e) 参数已填 | `## 通常需要按需求重定的参数` | 策划文档已明确给出该参数值，记录下来 |

---

### [6] 评估覆盖范围

**区分全覆盖与部分覆盖，措辞不同**：

- **全覆盖**：新需求的主要功能范围都被这个模式描述 → "你这个需求基本就是 P-XXX"
- **部分覆盖**：新需求只有某段功能被模式覆盖 → "你这个需求里的 [具体功能段] 部分像 P-XXX"

错误用法（禁止）：把部分覆盖说成全覆盖——"这个需求像 P-001"（当实际只有其中一块命中时）

---

### [7] 嵌入 Phase 1 第一回合输出

按模板组装 Phase 1 第一回合输出（见下方"输出模板"）。组装完成后直接输出，不额外说"我刚才查了库"之类的前置白话。

---

### [8] 退化路径

以下情况全部**静默**退化到原 Phase 1 标准结构，禁止输出"未找到库"或"查过没找到"：

| 情况 | 退化行为 |
|---|---|
| `.interaction-sop/` 目录不存在 | 静默退化 |
| `index.md` 不存在 | 静默退化 |
| 模式总览表为空（0 条 active 模式） | 静默退化；可在 Phase 4 完成后提议"要建模式库吗？" |
| 所有候选分数 < 阈值 | 静默退化 |
| `schema_version` 不匹配 | **例外**：提示一次"你的库 schema 落后，要升级吗？"；升级前不执行检索。如用户跳过升级，本次静默退化 |

---

## 打分公式

```
score = Σ(intent 命中) + Σ(ui 命中) - 2 × Σ(anti 命中)
```

**阈值自适应指引**：

- 阈值过低的症状：用户频繁说"这俩没关系" → 提高阈值或收紧 anti_signals
- 阈值过高的症状：用户说"这不是跟 P-XXX 很像吗，你怎么没提" → 降低阈值或补充 intent_keywords

Agent 在对话中应主动感知这两类信号并调整，不要等用户主动说"我发现你的模式匹配有问题"。

---

## ⚠️ 冲突处理

**硬规则 R1：Agent 不可替策划判定对错**

- 禁止自动按规范走：`"策划写错了，改成 P-001 的规则"`
- 禁止自动按策划走：`"这里策划有具体写法，直接用"`
- 必须：显式暴露冲突 → 等待用户拍板

**冲突段格式**（仅在有冲突时插入，平时不出现）：

```markdown
⚠️【N 处冲突需要你判断】（每条选"打破"或"回归规范"）

| # | 策划写 | P-XXX 骨架 | 备注 |
|---|---|---|---|
| 1 | [策划的描述] | [骨架原文] | [一句话背景或影响] |
| 2 | ... | ... | ... |

[若有关联]：[X] 的判定会连带 [Y] 的处理，一并说明。
```

**要点**：
- 每条冲突一行，不展开段落解释
- 备注列只写**最关键的一句话**（项目惯例 / 影响面 / 关联）
- 不列"两种可能"的具体说明——用户自己判断打破还是回归
- 如某条冲突后续影响很大，可在表格后追加**一句**说明，不超过 2 行

**冲突未拍板时的处理**：

用户在下一轮未对冲突表态（只回答了别的问题）时，下一轮 `我还需要确认` 的第一个问题 **MUST** 是该冲突。不得推进至 Phase 2，直到所有 `unresolved_conflicts` 清零。

## 模式成熟度措辞规则

根据命中模式的 `case_files` 数量调整措辞强度：

| case_files 数量 | 措辞风格 | 示例 |
|---|---|---|
| = 1（种子模式） | 软 | "以前在 [X] 做过类似，具体逻辑可能还会调整" |
| = 2（初步成熟） | 中性 | "以前在 [X] 和 [Y] 做过" |
| ≥ 3（稳定模式） | 硬 | "这是项目里的常用模式" |

## 输出模板

**硬规则 R-Output-1：Phase 0 内部过程禁止输出**

Agent 的内部检索过程（读了哪些模式、打分多少、命中阈值、三层标记明细）**一律不出现在用户可见输出中**。用户只看到：复述理解 + 相关历史建议 + 冲突表（如有）+ 待确认问题。

---

### 模板 A：命中 1 个模式，部分覆盖

```markdown
我当前理解：
- ...

这个需求初步属于：[类型]。

【相关历史 — P-XXX [模式名]】
项目里[模式一句话定位]已沉淀此模式。骨架是：[口语化核心逻辑，1-3 句]。

你这次可套用[骨架的 1-2 个核心要点]；[可调参数中策划已明确的，点出]。

⚠️【N 处冲突需要你判断】（每条选"打破"或"回归规范"）

| # | 策划写 | P-XXX 骨架 | 备注 |
|---|---|---|---|
| 1 | ... | ... | ... |

[关联说明，如有，1 句]

我需要确认：
1. [冲突判定（优先）]
2. [可调参数的具体问题]
3. [其他必要业务问题]

如果以上判断有问题，告诉我哪不对。
```

### 模板 B：命中 1 个模式，全覆盖

同模板 A，`【相关历史】` 段首句改为："你这个需求基本就是 P-XXX（[模式名]），以前在 [案例] 做过..."。

### 模板 C：命中 2 个模式

```markdown
我当前理解：
- ...

【相关历史】
这个需求里有两块以前做过：
- [需求的 A 部分] → P-001：[一句话骨架] | 要重定：[1 条]
- [需求的 B 部分] → P-002：[一句话骨架] | 要重定：[1 条]

⚠️【N 处冲突需要你判断】（每条选"打破"或"回归规范"）

| # | 策划写 | P-XXX 骨架 | 备注 |
|---|---|---|---|
| 1 | ... | ... | ... |

我需要确认：
1. ...

如果方向不对告诉我。
```

### 模板 D：命中 ≥3 个候选

同模板 A/B（展开最高分 2 个），在末尾追加：

```markdown
另外检索到 P-005 / P-007 可能相关，匹配度较低，要展开吗？
```

### 模板 E：无命中（退化）

直接按 `phase1-analysis.md` 原有标准结构输出，不提"查过没找到"。

## 会话级状态（Phase 0 结束后由 Phase 1 维护）

Phase 0 完成后，Agent 初始化以下会话级状态，由 Phase 1 持续维护：

```
adopted_patterns: []         # 已采用的模式 ID 列表
confirmed_facts: []          # 已确认事项（含模式骨架注入）
deviations_pending: []       # 待写入 deviations.md 的偏离点
unresolved_conflicts: []     # 未拍板的冲突（⚠️ 标记的）
pending_questions: []        # 剩余待问问题
```

此状态**仅存在于当前会话**，不持久化到磁盘。用户重新开始会话时从零初始化。
