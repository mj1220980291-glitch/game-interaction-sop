# Phase 1 — 需求挖掘

## 与 Phase 0 的衔接

Phase 1 第一回合开口前，Phase 0 会在内部完成项目模式库的检索与对比（见 `phase0-recall.md`）。Phase 0 的输出**嵌入**本 Phase 的第一回合输出中——不构成独立回合，不需要用户单独响应。

如果项目没有建模式库（`.interaction-sop/index.md` 不存在或模式表空），Phase 0 静默跳过，Phase 1 按原有标准流程走。

---

## 进入条件

用户给出需求：设计稿 / Figma 链接 / 策划文档 / 口头描述均可。第一回合先按「开场材料引导」确认有没有设计稿。

## 项目文风 mod（开口前读一次）

扫 `.interaction-sop/style*.md` 与 `style.config.json`，按契约 `../references/style-mod-schema.md` 的「文件选择顺序」决策，**只加载一份**。判断顺序自上而下，先命中先停：

| 命中项 | 行为 |
|---|---|
| `style_own.md` 存在 | 用 `style_own.md`，不询问 base；**若还有非基础 `style_<name>.md`** → 问一次是否切换，默认 `style_own.md` |
| 无 `style_own.md`，有 `style.md` | 用 `style.md`，不询问 base；**若还有非基础 `style_<name>.md`** → 问一次 |
| 无 `style_own.md` / `style.md`，有合法 `style.config.json` | 用 skill 内置 `style-base-<key>.md`，不询问；**若还有非基础 `style_<name>.md`** → 问一次 |
| 都没有 | **触发首次使用引导**（见下） |

- 记下该份的 `verbosity` / `role_annotation` / `wording` 与正文段，Phase 2 按它写；Phase 1 的提问纪律与冲突门禁不受影响
- **`schema_version` 不匹配** → 提示一次，用户不处理则本次用 `style.config.json` 指定 base，若 config 也无效则进新手引导
- **`style_<name>.md` 判定排除基础 3 份**：`style-base-regular.md` / `style-base-tri-section.md` / `style-base-detailed.md` 只是 skill 自带候选，不参与询问
- **`role_annotation.mode: never`** → Phase 2 不写 `- @职能：` 条目，Phase 4 也就不需要「职能标记」组件集
- `style.md` 与 base 文件都只读，任何 Phase 都不改写它们；沉淀永远落在 `style_own.md` 或本次选中的 `style_<name>.md`

## 首次使用引导（都空时触发）

命中条件：`.interaction-sop/` 下既无 `style_own.md` / `style.md` / 任意 `style_<name>.md`，也无合法 `style.config.json`。

### 第一回合固定话术

```
我注意到这是你第一次在这个项目里走 SOP。先选一种交互文档的表达风格，后续默认按它写：

1. 【常规 regular】3-6 条/簇，只在动效 / 新资源 / 关键逻辑处标 @职能
   适合：一般需求，产出轻量易读

2. 【三段式 tri-section】簇内固定三段「显示规则 / 状态说明 / 动效说明」
   适合：组件状态复杂、动效密集的需求

3. 【详尽 detailed】5-10 条/簇，每个相关职能都单独起一条 @职能
   适合：多方协作、职责边界敏感的需求

你喜欢哪一种？

💡 第一次使用，推荐三份都生成一次看看表达效果。回「都生成」我按同一份需求产出 3 份 md，
   你带到 Figma 对比后再选 —— 两条可选落地方式：
   （a）直接挑一种做默认（不生成 style_own，就用这份 base）
   （b）把一份改掉发回来，Phase 5 沉淀为 style_own.md，后续默认用它
```

### 分支处理

| 用户回复 | 行为 |
|---|---|
| 「1 / 常规 / regular」 | 本份文档用 `style-base-regular.md`；需求挖掘完 Phase 2 写一份 md；Phase 2 保存后把 `{defaultBaseStyle: "regular"}` 写入 `.interaction-sop/style.config.json` |
| 「2 / 三段式 / tri-section」 | 同上，base = `tri-section` |
| 「3 / 详尽 / detailed」 | 同上，base = `detailed` |
| 「都生成」/「3 份都要」 | 走「三份对比生成」子流程（见下） |
| 任意其他 / 跳过 | 本份文档静默用 `regular` 做默认，不写 config；下一次打开仍会问一次 |

### 三份对比生成子流程

用户选了「都生成」时：

1. 正常走 Phase 1 需求挖掘，直到冲突清零（这一步**只做一次**，三份 md 共用同一份理解）
2. Phase 2 **连续产出 3 份 md**，各用一份 base，文件名加后缀：
   - `<需求名>_交互文档_regular.md`
   - `<需求名>_交互文档_tri-section.md`
   - `<需求名>_交互文档_detailed.md`
3. 三份都保存后，提示用户：

```
三份 md 已生成完毕。建议你带到 Figma 对比表达效果，然后告诉我：
- 「用 regular / tri-section / detailed」→ 我把这份记为默认，后续新需求就按它写
- 「改了 X 版，看看这版」→ 发修改后的 md 回来，Phase 5 沉淀为 style_own.md
```

4. 用户确认选哪份 → 写 `style.config.json`；若用户发回改稿 → 走 Phase 5 沉淀路径（见 `phase5-style-learn.md`）
5. 本阶段最多走一次；用户若全部拒绝 → 本次静默用 `regular`，不写 config

### 写入 `style.config.json`

```json
{
  "schema_version": 1,
  "defaultBaseStyle": "regular"
}
```

- 写前检查目录存在，不存在就创建 `.interaction-sop/`
- 文件已存在时覆盖（备份 `.bak`）
- `defaultBaseStyle` 只能是 `regular` / `tri-section` / `detailed`

## 完成条件

下列**全部 5 项**同时满足才可进入 Phase 2：

1. 已采用模式（若有）的"通常需要重定的参数"全部明确
2. 已采用模式（若有）的"容易需要重新决策的地方"中，新需求触及的点已拍板
3. 未被模式覆盖的业务专属问题：核心触发/对象/目标/输入/状态/反馈/边界都明确
4. 会话级状态 `unresolved_conflicts` 为空（所有 ⚠️ 冲突已拍板）
5. **完成声明已落盘并通过机器校验**（见下节「完成声明」）

> **即使用户说"直接写完整 Markdown"，只要有未决冲突（`unresolved_conflicts` 非空），仍 MUST 先定冲突再推进。**
>
> **只有对话里的自述不算完成。** 第 5 项是唯一可被工具验证的产物；没有它，Phase 2 不得开工（见 `phase2-markdown.md` 进入条件）。

不要追求完美确定。够用就推进——但冲突必须清零。

## 完成声明（Phase 2 的硬门禁）

Phase 1 收尾时，**必须**把挖掘结果写成一份机器可校验的 JSON，落到
`<项目根>/.interaction-sop/phase1-signoff.json`，然后调用
`validate_phase1_signoff`（MCP：`figma-interaction-doc-engine`）拿到 `ok: true`。

```json
{
  "schema_version": 1,
  "requirement": "<需求名，与 Markdown 标题一致>",
  "checked_at": "2026-11-03",
  "unresolved_conflicts": [],
  "pending_questions": [],
  "dimensions": {
    "params": true,
    "diff_areas": true,
    "business": true,
    "conflicts": true
  },
  "evidence": {
    "params": "冷却 8s / 上限 3 层（策划文档 2.1）",
    "diff_areas": "P-003 骨架已拍板复用",
    "business": "触发、输入、状态、反馈、边界已问清；归属见 @程序/@策划",
    "conflicts": "1 处冲突已拍板：内嵌（用户选）"
  }
}
```

校验规则（引擎只认这四条，不做语义解释）：

| 字段 | 必须 |
|---|---|
| `schema_version` | `1` |
| `unresolved_conflicts` | `[]` |
| `pending_questions` | `[]` |
| `dimensions` | `params` / `diff_areas` / `business` / `conflicts` 全为 `true` |

- 任一条不满足 → 工具返回 `ok: false` + 具体错误码（`V2_SIGNOFF_CONFLICTS_OPEN` / `V2_SIGNOFF_PENDING_QUESTIONS` / `V2_SIGNOFF_DIMENSIONS_INCOMPLETE` / `V2_SIGNOFF_INVALID`）。**回去继续挖，不要改声明凑数**
- 文件不存在 → `V2_SIGNOFF_FILE_MISSING`；传 `signoff` 对象可直接校验（不落盘时引擎仍会接受，但 SOP 要求落盘，便于复盘）
- Phase 4 渲染时把这个对象一起传给 `render_v2_markdown_to_figma` 的 `phase1Signoff`：不合格会被硬拒绝，不传则返回 `V2_W_PHASE1_SIGNOFF_MISSING`

**为什么要这条**：SOP 原文「4 维度全满才可进 Phase 2」全靠 agent 自觉，没有强制产物，结果需求常常在文档写完之后才补挖。声明落盘 + 工具校验是唯一能让这条规则"有牙齿"的方式。

## 逐帧校验（需求来自 Figma / 截图时，硬规则）

**只要需求材料里包含 Figma 链接 / 设计稿 / 截图，Phase 1 结束前必须逐帧截图核对，核对完才允许成文。**

1. 逐帧 `figma_capture_screenshot`（或 `figma_take_screenshot`；只能截视口时先 `figma_execute` 定位节点）
2. 每帧核对四类事实，**以图为准，不以文字推断**：
   - 控件清单（图上有的才算有，图上没有的不许补）
   - 文案（按钮 / 标题 / 占位符原文，逐字抄）
   - 布局（左右分栏、消息对齐方向、dock 位置）
   - 状态差异（同一界面的多态用气泡分别标注哪些控件变了）
3. 产出**帧清单**并回给用户确认：

```
逐帧核对清单（N 帧）
- 图1「登录命名」：控件 6 个（标题/输入框/骰子/确定/提示/背景按钮）；左对齐；…
- 图2「好友申请」：3 行列表，行高一致，右侧按钮「同意」；…
```

4. 截图不可用（Bridge 断 / 工具报错）时：写明"逐帧核对未完成，按文字材料成文，偏差风险由你确认"，**不要**假装核对过
5. 帧数 > 8 时先截前 8 帧并在清单里标 `待核对`；成文前把剩余帧补完，或明确标注哪几章基于文字

> 本轮真实偏差（好友行内容、消息对齐、面板左右 dock）全部来自"按文字提取成文、没逐帧看图"。这条规则的目的是把偏差挡在 Phase 2 之前。

## 开场材料引导（设计稿优先）

Phase 1 第一回合开口前，**先要设计稿，再谈策划文档**。固定开场：

```
我先确认材料：这个需求有设计稿吗？

1. 有图 → 直接发图片，或给 Figma 链接（指向具体界面节点即可）。我按图组织问题，策划文档只用来补图上看不出的规则
2. 还没有 → 把策划文档发我，我按文档梳理；需要的话我先画一版界面草稿确认章节骨架

两种都行，没有图也不卡流程。
```

- 有图 → 路径A：以图为骨架提问，不问"这个界面长什么样 / 有哪些控件"
- 明确没图 → 路径B：转策划文档，MAY 提议先画草稿
- 既没图也没文档 → 按口头需求问 1-3 个问题
- 设计稿**不是硬前置门禁**：用户说没有就往下走，**同一阶段内**不准反复索要
- 开场话术只出现一次；用户已主动贴图或贴链接时跳过提问、改写成确认句（见「第一回合标准结构」硬约束）

## 入场材料识别（双入口）

材料类型由上面的「开场材料引导」问出（用户已主动给图时直接判定），再决定走哪条路径。**默认先问图**，策划文档只是规则补充源。

```
路径A（图先行，主流）              路径B（策划文档先行）
用户给草稿/截图/设计稿             用户只给策划文档，无任何图
（无论是否同时给策划文档）              │
    │                             Agent 可主动提议：先画一版
    │                             界面草稿确认章节骨架
以图为骨架提问，                       │
策划文档降为规则补充源            草稿载体不限——Figma 低保真 /
    │                             HTML demo / 文字界面态速写，
    │                             由 Agent 按需求复杂度与工具
    │                             可用性自行判断（skill 不规定）
    │                                  │
    │                             用户确认草稿（仅作章节骨架，
    │                             不追求视觉精确）
    │                                  │
    ▼                                  ▼
    └──────► Phase 2 Step 0.1 界面清单 = 图清单 ◄──────┘
```

**路径A（入场时已有图）**：
- Agent SHALL 以图为骨架组织提问（"这张图上有哪些控件 / 这个控件怎么触发"），**不再要求用户描述界面结构**——结构从图直接读
- 策划文档（若有）仅用于补充图上看不出的规则细节（数值、边界、服务端逻辑）
- Phase 2 Step 0.1 的界面清单直接锚定这些图（一图一章）

**路径B（仅有策划文档）**：
- Agent MAY 主动提议"先画一版界面草稿（或文字速写）确认有哪几张图"，让用户确认章节骨架
- 草稿载体不做规定，Agent 自行判断（Figma / HTML / 文字速写均可）。草稿仅用于确认"界面态清单"，不追求视觉精确
- 用户确认草稿后，流程汇入路径A，Phase 2 Step 0.1 锚定草稿图清单
- 用户拒绝画草稿时，Agent SHALL 直接以文字版界面态清单走 Step 0.1（每项附"这张图上应能看到什么"速写）

> 路径识别不改变完成条件与冲突清零门禁——两条路都要把 `unresolved_conflicts` 清零才进 Phase 2。

## 采用契约（会话级状态）

Phase 1 期间 Agent 维护以下 5 个会话级状态，**不持久化到磁盘**：

```
adopted_patterns: []
  已采用的模式 ID 列表（如 ["P-001", "P-003"]）
  
confirmed_facts: []
  已确认事项列表，含两类：
    · 用户明确答复的事项
    · 由 adopted_patterns 骨架自动注入的决策
  
deviations_pending: []
  待写入 deviations.md 的偏离点列表
  格式：[(模式 ID, 偏离描述, reason)]
  
unresolved_conflicts: []
  未拍板的冲突列表（来自 Phase 0 的 ⚠️ 标记）
  
pending_questions: []
  剩余待问问题（模式可调参数 + 差异领域 + 业务专属）
```

用户**中途撤销采用**（见"中途撤销采用"段），Agent 回滚相关状态并重算 `pending_questions`。

会话结束后状态自动丢弃。重开会话时从零初始化，Phase 0 重新执行检索。

## 第一回合标准结构

> **硬约束**：第一回合 = **材料确认句 + 下列结构**。材料确认句见上文「开场材料引导」，必须放在模板最前，**不准省略、不准先讲"我当前理解"**。用户已主动贴图 / 贴链接时，材料确认句改成"图我收到了，先按图看"。下面的模板已内置这句，照抄即可。

**情况 A：Phase 0 有命中（嵌入咨询式建议）**

```markdown
先确认材料：这个需求有设计稿吗？
- 有图 → 直接发图片，或给 Figma 链接（指向具体界面节点），我按图提问
- 还没有 → 发策划文档，我按文档梳理；需要的话先画一版界面草稿

我当前理解：
- ...

这个需求初步属于：[类型]。

【相关历史 — P-XXX [模式名]】
项目里[模式一句话定位]已沉淀此模式。骨架是：[口语化核心逻辑，1-3 句]。

你这次可套用[骨架的 1-2 个核心要点]；[策划已写明的可调参数，点出]。

⚠️【N 处冲突需要你判断】（仅在有矛盾时出现，每条选"打破"或"回归规范"）

| # | 策划写 | P-XXX 骨架 | 备注 |
|---|---|---|---|
| 1 | ... | ... | ... |

[关联说明，如有，1 句]

我需要确认：
1. [冲突判定（优先）]
2. [可调参数的具体问题]
3. [其他必要业务问题]

如果以上判断有问题，告诉我哪不对。
```

**情况 B：Phase 0 无命中或无库（原标准结构）**

```markdown
先确认材料：这个需求有设计稿吗？
- 有图 → 直接发图片，或给 Figma 链接（指向具体界面节点），我按图提问
- 还没有 → 发策划文档，我按文档梳理；需要的话先画一版界面草稿

我当前理解：
- ...

这个需求初步属于：[类型]。

我先确认 1-3 个会影响交互文档落地的问题：
1. ...
2. ...
3. ...
```

**禁止在第一回合输出**：风险点、验收点、完整交互文档、示意图清单、实施计划、OpenSpec proposal/tasks/spec。

跳过提问的唯一例外：用户显式说"不要提问 / 直接输出 / 不用追问"，或会话已经包含全部关键决策的答案。跳过时必须说明为什么跳过。

> **例外约束**：即使用户说跳过，`unresolved_conflicts` 仍不能跳过，见完成条件第 4 项。

## 后续回合标准结构

```markdown
已确认：
- [用户明确答复的事项]
- [采用 P-XXX（模式名称）：]（仅在有 adopted_patterns 时出现）
   · [骨架注入的决策 1]
   · [骨架注入的决策 2]
   · ...

[偏离备忘]（仅在 deviations_pending 非空时出现）
- [偏离点描述]（偏离 P-XXX，准备记入 deviations.md）

我还需要确认：
1. [最重要的未决冲突（若有，必须排第一）]
2. [可调参数问题]
3. [其他业务专属问题]
```

**提问优先级**：
1. `unresolved_conflicts` 中的冲突（必须最先问，直至清零）
2. 已采用模式的可调参数
3. 差异领域命中的具体点
4. 业务专属问题（通用分类法）

**骨架已锁定的问题不再问**：已在 `confirmed_facts` 中由模式注入的骨架决策，不得作为后续轮的追问对象。

每轮 ≤ 3 个问题，最关键的一个就够。用户答完，先把答案变成`已确认`再问下一轮。

## 提问的判断标准

**应当问**：会改变以下任何一项的问题——

- 触发条件
- 目标对象/命中区域
- 输入方式（点击/hover/快捷键/拖拽/长按/平台手势）
- 可见 UI 状态
- 成功/失败反馈
- 动效/音效序列
- 资源/数据/配表规则
- 边界情况
- 平台差异
- 下游交付物

**不应当问**：低影响视觉偏好、字号、颜色（除非影响可读性/遮挡/适配）。

**路径A 提问纪律（入场时已有图）**：界面结构从图直接读，**不再问用户"这个界面长什么样 / 有哪些控件"**——这类问题在路径A 下是冗余的。提问聚焦图上**看不出**的规则细节：控件的触发条件、数值阈值、状态切换逻辑、边界情况、服务端约束。

## 完成度评估

**4 维度全部满足 → 信息可用，进入 Phase 2**：

1. **可调参数齐**：已采用模式的"通常需要按需求重定的参数"全部明确（无模式则跳过）
2. **差异领域定**：需求触及的"容易需要重新决策的地方"全部已拍板（无模式则跳过）
3. **业务专属齐**：触发/对象/目标/输入/状态/反馈/边界/下游/交付物中，影响 v2 Markdown 落地的全部明确（允许少量`待补充`）；影响交付的**职能归属**已问清（策划配表 / 服务端控制 / 动效实现等），归属不明的进 `⚠ 待确认`，不留给 Phase 2 猜
4. **冲突已清零**：`unresolved_conflicts` 为空

**信息充分**：4 维度全满 + 无任何`待补充`，v2 Markdown 可定稿无遗留。

不要追求完美确定。够用就推进——但冲突必须清零，不可例外。

## 中途撤销采用

用户在 Phase 1 后续轮、Phase 2、Phase 3、Phase 4 的任意时点说出以下类型的语言，Agent 应识别为"撤销采用"意图：

- "P-XXX 不合适" / "这个不要参考之前的" / "换个思路，不复用了"
- "把刚才的模式撤掉" / "重新来"

**状态回滚**：

```
1. adopted_patterns 中移除对应模式 ID
2. confirmed_facts 中删除由该模式注入的骨架条目（保留用户自答的事项）
3. deviations_pending 中清除该模式的偏离条目
4. pending_questions 按原 SOP 分类法重算（补回被骨架替代的问题）
5. unresolved_conflicts 清除该模式相关的冲突
```

**落盘处理**：
- 如 Phase 2 的 Markdown 尚未落盘 → 重新进入 Phase 2 按新状态写
- 如 Phase 2 的 Markdown 已落盘 → Agent 提议：先存 `.bak` 备份，再重写
- 如已进入 Phase 4（Figma 写入）→ 提议重新从 Phase 2 开始

Agent 输出撤销确认：

```markdown
好，撤销 P-XXX。
以下骨架决策已从"已确认"中移除：
- [原注入的骨架 1]
- [原注入的骨架 2]
- ...

这些问题需要重新讨论：
1. [从骨架中来的、需要重新确认的问题]
2. ...
```
