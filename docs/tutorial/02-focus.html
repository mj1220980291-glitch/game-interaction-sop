交付前，照这张清单勾一遍

不用记流程。文档写完、写进 Figma 之后，从下面三组里逐项勾。全勾上就是能交的文档，勾不上的地方就是还要改的地方。

先确认走的是哪条路

一、内容与结构

勾什么怎么判断
文件头四行齐全 跟进UI、需求组、易协作链接、最后更新时间，顺序没变
设计总览只有一个 里面只有功能背景和核心交互两块，没有第三个小标题
章节编号连续 01、02、03 不跳号，名字里带界面关键词
每个簇第一行有角色标记 角色和实际负责的职能对得上，不是全写成一个
每条规则都能在图上找到落点 指着这条规则，能在设计稿上指出对应的控件或状态
状态行没有被打断 同一控件连续写状态，中间没夹进普通规则
反馈写了 提示、音效、特效，实际会有的那几个都在
边界写了 满了、冷却中、断线、重复点击，至少覆盖这次会遇到的

二、配图

勾什么怎么判断
每条配图都能对上来源 清单里每行都有节点或截图，写「保留占位」的也算对上了
图里没有画外内容 截的区域只包含这条规则要说明的东西，没带进别的界面
主图是真实实例或清晰设计稿 不是低分辨率截图，放大后文字还清楚
没图的簇写明了理由 写的是「配图：无（理由：…）」，不是空着

三、Figma 成品

勾什么怎么判断
文档没压在设计稿上 先看位置和图层顺序，再看内容
每个簇都有说明块 没有哪个簇只有气泡、没有文字说明
标号指向正确控件 逐个看图上的数字，对不上就调锚点，别改文字
没有多余空图框 画布上没有剩下的小灰框
缺图提醒处理完了 每条要么补图，要么明确说这次不要
三处最容易漏
  • 标号位置：默认按网格摆，会排成一条斜线，要逐章给锚点。
  • 状态行：写状态时容易顺手插一条普通规则进去，整段识别会乱。
  • 同步：改完 Markdown 再跑一次同步，Figma 里那份不会自动更新。
