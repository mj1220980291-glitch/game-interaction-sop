## Context

game-interaction-sop 的 skill（`packages/skill/`）是 LLM 侧 SOP，通过 Phase 0–5 引导 AI 把策划需求转成 v2 Markdown，再由引擎写入 Figma 模板 1:14。

两个真实交付案例的 diff 表明：引擎渲染层无问题（骨架、气泡、说明块都对），问题全部出在 **skill 指导 LLM 产出的文本层**——

- 十一主城联动玩法（流程型策划稿入场）：设计师重排章节（逮捕按钮移章、押送/雾效/落地反馈整簇删除）、合并 bullets、改术语。结构层+转写层双重返工。
- 变色龙躲藏者（界面型策划稿入场）：章节结构未动，但 bullets 合并、删预留交互/开关反面、新增 toast 反馈与（待设计）标记。转写层返工。

与用户（设计师本人）对齐后的关键结论：

1. 入场材料**不一定是策划文档先行**，大部分场景是图先行（草稿/截图/设计稿在手），策划文档只是规则补充源；也存在"只有策划文档，让 AI 先画一版草稿"的路径。
2. 草稿载体可能是 Figma 绘制或 HTML demo——**skill 不需要详细规定**，保留可能性让 AI 自行判断即可。
3. UI 反馈补全（toast/浮显等）不是靠 Phase 1 提问挖出来的，而是 Phase 2 输出文档时 LLM **应该主动想清楚**的转写完整性问题。
4. 角色喊话句、设计 rationale、类比锚定、（待设计）后缀等 L3 设计增值内容——人为补充，SOP 不修。
5. "待策划确认"行内标记是 LLM 绕过 Phase 1 冲突清零门禁的自发行为（skill 并无此要求，反而明令禁止待确认簇名），加一条自检堵住即可，不需要三态标记规则体系。

约束：

- 引擎（`packages/figma-mcp-server`）parser 校验码不动——本次全部是 LLM 转写层规则，不新增 hard error / soft warning。
- `markdown-v2-spec.md`（skill 侧）与 `openspec/specs/markdown-v2-contract/spec.md`（主 spec）有双向一致约束（skill-sop-workflow 既有 Requirement），两侧必须同步修改。
- 历史已产出的 v2 Markdown 文档不需要迁移——新规则只约束生成行为，不改机器契约。

## Goals / Non-Goals

**Goals:**

- 章节划分锚定"一张可截图的界面态"（图先行），消灭流程章导致的结构性返工
- 支持双入场路径：图先行（路径A）与策划文档先行 + AI 画草稿（路径B）
- bullet 文体对齐设计师实际习惯：完整行为叙述 + 强调项独立，废除原子化
- 图上不可见的内容（服务端规则/纯演出/预留交互/开关反面）显式丢弃而非收录
- UI 反馈补全成为 Phase 2 输出的主动自检项
- 堵住"待确认"行内标记泄漏

**Non-Goals:**

- 不改引擎代码、parser 校验码、渲染逻辑
- 不动 S3 章节名白名单（"场景"关键词保留——违规的是按流程切章这个行为，由 skill 层约束，不由 parser 拦截）
- 不处理 L3 设计增值层（喊话句/rationale/类比/（待设计）后缀）——人为补充
- 不建立（暂定）/（待设计）/待确认的三态标记规范——特殊情况说明，不立规则
- 不规定路径B 草稿的具体载体与产出标准

## Decisions

### D1. 双入口在 Phase 1 入场处分流，在 Step 0.1 汇合

```
路径A（图先行，主流）              路径B（策划文档先行）
用户给草稿/截图/设计稿             用户只给策划文档
    │                                 │
    │                             AI 产出一版草稿
    │                             （Figma/HTML/文字速写，AI 自行判断）
    │                                 │
    │                             用户确认
    │                                 │
    ▼                                 ▼
    └────────► Step 0.1 界面清单 = 图清单（一图一章）◄────────┘
                    │
               Step 0.2 每张图列可指认控件 → 簇
                    │
               Step 0.3 策划稿规则归位 + 显式丢弃清单
                    │
               Step 0.4 终态确认 → 写 Markdown
```

理由：不改 Phase 编号体系（避免 SKILL.md 大重排与历史归档 change 语义漂移），只在 Phase 1 增加"入场材料识别"、在 Phase 2 Step 0.1 前置"图清单锚定"。备选方案是新增 Phase 1.5"要图/画草稿"独立阶段——否决，因为路径B 的草稿产出与确认天然属于需求挖掘对话的一部分，独立成 Phase 会让门禁表复杂化。

路径B 草稿载体刻意**不写细则**：只在 phase1-analysis.md 中说明"仅有策划文档时，可主动提议先画一版界面草稿（形式不限）供用户确认章节骨架"。理由：用户明确说"不需要详细写进 skill，保留可能性让 AI 做就好"。

### D2. Step 0.3 从"穷尽归位"改为"归位 + 显式丢弃清单"

现状 Step 0.3 要求策划稿**每条**规则归位到 (界面, 模块)，归位不上的 flag 为"疑似漏界面/漏模块"——导向是穷尽收录，导致服务端规则、纯演出内容被硬塞进簇（十一案例的"押送跟随行为""高空环境切换流程"）。

改为三分法输出：

```
规则归位（草案）：
✓ 规则 1 → 界面 N . 模块 M
✗ 规则 X → 丢弃（理由：纯服务端逻辑，图上无 UI 表现）
✗ 规则 Y → 丢弃（理由：纯演出，无控件可指）
⚠ 规则 Z → 无法判断（疑似漏界面/漏模块，需用户确认）
```

丢弃判据（写入 phase2-markdown.md）：纯服务端规则（时长/并发/解除条件由服务端控制且无 UI 表现）、纯环境演出（雾效/天空盒切换）、预留不开发的交互、开关的反面陈述（"关闭时不铺底色"这类显然内容）。丢弃不是静默的——必须列给用户确认，用户可推翻。

### D3. W4 重写为"完整行为叙述"粒度，配"强调项独立"例外

现状 W4 要求"长复合规则拆多条"。两案例 diff 一致表明设计师反向操作：同一控件的常规规则合并成一句流畅叙述，只有需要强调/有风险的点独立成条。

新 W4 表述：

> 一条 bullet = 一个完整行为叙述（可含多动作串联，如"W/A/S/D 四键移动角色，按住 Shift 加速跑，按空格跳"）；需要强调、有风险、或需要角色特别注意的点独立成条（如"需要注意，按下时光标从当前选中动作位置处出现"）。同一控件的规则不在多个簇间分裂——跨簇时归位合并到该控件所属的簇。

引擎不校验 bullet 粒度，此规则仅约束 LLM 生成与 Phase 2 自检。

### D4. UI 反馈补全落在 Phase 2 自检清单，而非 Phase 1 提问

理由：用户确认这类内容"不是固定有的，比较难问出来"，提问钩子挖不到。它是转写完整性问题：LLM 写每个控件簇时，应自问"这个操作/状态有没有可见反馈"，策划稿未写时按常识补一条反馈描述（toast/浮显/高亮/音效），以正常陈述语气写入，不加待确认标记——与"待确认全删"原则自洽（反馈缺失是设计师该拍板的事，不是开放问题）。

### D5. "待确认"行内标记进自检清单，定性为门禁泄漏信号

phase2-markdown.md 自检清单新增一条：文档内不得出现"待确认/待拍板/待策划确认"类行内标记。出现即说明 Phase 1 冲突清零门禁被绕过（LLM 把未拍板冲突降级成行内备注），处理方式是回退 Phase 1 拍板，而不是保留标记。不建立三态标记规范——（暂定）保留、（待设计）进标题均属特殊情况的自然说明，不立规则。

### D6. markdown-v2-contract 主 spec 用 ADDED 而非 MODIFIED

W4 原子化条款只存在于 skill 侧 `references/markdown-v2-spec.md`（软约束表），主 spec 中没有对应 Requirement 块——所以主 spec 侧全部是 ADDED（bullet 粒度、不可见内容丢弃、术语跟随、反馈补全、同控件归位合并），skill 侧文件同步改写 W4 与新增条款。既有 Requirement"skill 文档与 OpenSpec 主 spec 双向一致"保证两侧不漂移。

### D7. Phase 3 在路径A 下退化，但不删除 Phase

路径A 入场时图已在手，Phase 3 的"索要设计稿"退化为"收集高清资产/确认贴图"。保留 Phase 3 编号与门禁（Phase 4 前仍需资产确认或显式跳过），只简化话术。理由：删除 Phase 会牵动 SKILL.md 门禁表、输出契约表、全部 phase 文件交叉引用，成本大于收益；且路径B 场景下 Phase 3 仍承担完整职责。

## Risks / Trade-offs

- **[图清单误判]** 路径A 中用户给的图可能是局部截图/多态对比图而非完整界面态，Step 0.1 按图切章可能切错粒度 → 缓解：Step 0.1 保留既有"多态拆分指南"判断（模块差异 ≥ 2-3 拆章），并保留用户对清单的审核确认门。
- **[丢弃过度]** Step 0.3 丢弃判据由 LLM 执行，可能把有 UI 表现的规则误判为"纯服务端" → 缓解：丢弃必须显式列清单给用户确认，不静默；⚠ 无法判断项仍走原"疑似漏界面"通道。
- **[路径B 草稿质量]** AI 画的草稿可能误导章节划分 → 缓解：草稿仅作章节骨架确认用，用户确认后才进 Step 0；skill 措辞明确草稿"不需要精确，只需要覆盖界面态清单"。
- **[W4 与旧文档不一致]** 历史 v2 Markdown 按原子化写，新规则下风格不同 → 接受：历史文档不被重新校验，风格差异无功能影响。
- **[双侧文件漂移]** skill 侧 references 与主 spec 修改不同步 → 缓解：tasks 中把两侧修改绑定为同一任务项，验收时对照。

## Migration Plan

纯 Markdown skill 文件修改，无数据迁移。实施后运行 `npm run install-skill -- --agent <agent> --force` 同步到各 agent 即生效。回滚 = git revert。
