## Context

- 簇内 bullet 在 IR 里是纯字符串（`SemanticCluster.groups[].bullets`），render 用 `normalizeBulletText` 去掉前缀后写进 `正文/规则` TEXT。目前所有 bullet 字重一致，`状态·xxx：` 只是普通文字。
- 文字写入有三条路径，最终都在插件里设置 `characters`：
  1. `render.ts` 无配图扁平路径 → `setMultipleTextContents`
  2. `render.ts` 原位配图 / `####` 路径 → `appendBulletsInOrder` 收集 `textUpdates` → `finishBlockFigures` → `setMultipleTextContents`
  3. 同步模式 `reconcile/plan.ts` 的 `setText` op → `applyOps`。新增节点走临时文档渲染（路径 1/2），再搬过来
- Figma 设置 `characters` 时，新文字沿用原首字符的样式。原来以粗体开头的 TEXT 改成普通规则后会整行变粗，所以加粗必须显式写入，也必须显式清除。
- 字体加载有节流（第 7 次起约 1s/次），批量写入已按字体去重；新增的粗体字重也必须纳入去重。

## Goals / Non-Goals

**Goals:**
- 状态行的识别只有一份实现，parser、render、reconcile 共用。
- 状态名加粗，三条写入路径表现一致；同步模式改文字后，加粗状态与文字一致。
- 不含状态行的文档，渲染调用序列不变（`BASELINE_CALL_SEQUENCE` 不动）。
- 叙述顺序以写作规则为主，引擎只检查能机械判断的一点（状态行连续）。动效句无前缀，引擎不识别。

**Non-Goals:**
- 不做横排状态图墙，不改模板结构。
- 不让状态行自动带配图；配图仍是单独的 `配图：` 行，`NN/C/K` 计数规则不变。
- 不对"是什么 / 交互 / 反馈"做语义判断，也不做硬校验。
- 旧 `状态·` 写法只提醒，不自动改写；已交付文档不回改。

## Decisions

### D1 状态行识别规则（`v2/state-line.ts`）

`parseStateLine(text) → { name, nameEnd } | null`，输入为 `normalizeBulletText` 之后的文字：

1. 取第一个 `：` 或 `:` 之前的部分作为 head；没有冒号时 head 为整行。
2. head 去空白后须以"状态"结尾，长度 3–10 个字符（至少 1 个字 + "状态"），且不含 `，,。；;、` 等标点。
3. 以 `配图`、`动效需求` 开头的行一律不算。
4. `nameEnd` = head 在原文中的结束位置（不含冒号），即加粗范围 `[0, nameEnd)`。

示例：`默认状态` ✅ 整行加粗；`冷却状态：技能释放后进入` ✅ 加粗"冷却状态"；`进入战斗状态后显示血条` ❌（无冒号且超过 10 字）；`角色进入观战状态：xxx` ✅ 也会命中——这类写法按规范本来就该是状态行，接受。

备选：用显式标记（如 `- [状态] 冷却`）。被否：用户明确要求自然中文，不加前缀符号。

### D2 加粗范围随文字一起下发

- `setMultipleTextContents` 的 update 和 `applyOps` 的 `setText` op 增加可选字段 `bold?: number`（加粗字符数）。
  - 字段缺省：行为与现在完全一致（标题、表头、编号等不受影响）。
  - `bold: 0`：写入后把整段设为常规字重（用于 bullet 由状态行改为普通规则）。
  - `bold: n > 0`：写入后整段设为常规，再把 `[0, n)` 设为粗体。
- render 和 reconcile 在写 **bullet 正文**时始终带上 `bold`（命中状态行为 `nameEnd`，否则为 0）。由于首次渲染时克隆来源是模板的常规字重 TEXT，`bold: 0` 只是一次 `setRangeFontName`，不增加 RTT。

备选：插件侧自己识别状态行。被否：识别规则会在 TS 和插件脚本字符串里各写一份，容易漂移。

### D3 常规 / 粗体字重的解析（插件侧）

每次调用、每个字体族只解析一次，结果放进本次调用的 Map：

- **常规**：取节点现有字体中不属于粗体候选的那个；如果节点整段都是粗体（例如上次是只有名字的状态行），回退到同族的 `Regular`。
- **粗体**：同族按 `Bold` → `SemiBold` → `Semibold` → `Medium` 依次尝试 `loadFontAsync`，第一个成功的为准。
- 需要的字重和原有字体一起去重后加载，节流成本最多多 1–2 次加载。
- 找不到粗体时只写文字、不加粗，返回值中带上该字体族，由引擎记一条软警告 `V2_W_STATE_BOLD_UNAVAILABLE`，不中断渲染。

实现前先在「Agent草稿」模板上确认正文 TEXT 的字体族和可用字重，写进 tasks 的验证项。

### D4 同步模式

- `plan.ts` 的 text 判定表（D5）仍只比较文字：文字相同即认为一致，不检查字重，所以设计师手动取消加粗不会被当作冲突，也不会被改回。
- 生成 bullet 的 `setText` op 时附带 `bold`（同 D2）。
- 标记（stamp）里存的 `text` 不变，加粗完全由文字推导，无需迁移旧标记。

### D5 软提醒（parser）

按 `####` 分组（无 `####` 时即整簇）检查，`配图：` 行不参与判断：

| 码 | 触发 |
|---|---|
| `V2_W_STATE_LINES_SCATTERED` | 同组内状态行之间夹着普通规则 |
| `V2_W_LEGACY_STATE_PREFIX` | bullet 以 `状态·` / `状态｜` 开头，提示改为"xx状态：…" |

两条都只提醒，不阻断渲染。

曾有第三条 `V2_W_MOTION_NOT_LAST`（`动效需求：` 之后还有规则），2026-10-18 用户决定动效句去掉前缀后删除：无前缀时只能靠关键词猜，误判风险大于收益，顺序交给写作规范与 phase2 自检。

### D6 写作规则（skill + 主 spec）

- T9 簇内叙述顺序：① 是什么（作用、何时出现、数据来源；不写可见的位置外观）→ ② 怎么交互（操作 → 直接结果；不形成状态的边界情况紧跟对应交互）→ ③ 有哪些状态 → ④ 反馈（toast / 音效 / 特效，动效句最后）。没有的段跳过。
- T8 动效句：直接写"什么情况下，需要什么样的动效"，无 `动效需求：` 前缀、不用冒号。冒号说明格式只属于状态行，两者靠格式区分。
- 状态块写法：冒号后写出现条件，不写外观；简单状态只写名字；每个状态后可跟一条 `配图：`。
- T7、W3 中的 `状态·` 示例全部改为新写法。

## Risks / Trade-offs

- [普通句子被误判为状态行，例如"技能状态：…"本意是规则] → 规则限定 head ≤ 10 字且以"状态"结尾；误判的后果只是几个字加粗，不影响结构。写作规范里给出反例。
- [模板字体族没有粗体字重] → D3 回退 + 软警告；实现前先在真机上确认。
- [加粗多一次 `setRangeFontName` 拖慢批量写入] → 纯本地操作，不涉及 RTT；粗体字重只加载一次。
- [Figma 首字符样式继承导致残留加粗] → bullet 写入时始终显式下发 `bold`（含 0），不依赖继承。
- [已有文档仍是 `状态·` 写法] → `V2_W_LEGACY_STATE_PREFIX` 提醒；旧写法按普通 bullet 渲染，和现在一致。
