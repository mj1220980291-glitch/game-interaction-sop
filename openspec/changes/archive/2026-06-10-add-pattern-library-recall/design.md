## Context

`game-interaction-sop` 是一个跨项目分发的 skill（Markdown 文档形式）。它通过 4 个 Phase 把策划需求转化为 Figma 交互文档。当前 Phase 1 完全依赖通用分类法提问，不与项目已有设计建立联系。

历史上的「全局规范文档」（例如 `局外系统/specs/局外系统交互框架/`）已被弃用，原因是粒度过粗、与具体需求脱钩。本次设计基于以下事实：

- 项目真正的资产沉淀在散落的"交互文档"中（30+ 个 .md 文件），它们是"案例"而非"规则"
- skill 需要通过 git 仓库分发，不能假设任何项目目录结构
- 用户不愿手写格式严格的规范文档，但可以接受 review Agent 提取的结果
- LLM 擅长读 + 对比 + 给建议，不擅长机械化的"是否套用"查询

## Goals / Non-Goals

**Goals:**

- 引入"项目级模式库"机制，让 Phase 1 在提问前先翻库
- 输出形态为**咨询式建议**（"以前在 X 做过，逻辑是 Y，我建议..."），而非机械的"命中 P-001，是否套用"
- 主动识别"策划文档 vs 项目规范"的冲突，让用户拍板，不替策划判定对错
- 模式库内容由 Agent 自动提取与维护，用户负担最小化
- skill 仓库与项目仓库职责清晰分离：skill 携带 schema + 协议，项目携带数据
- 未建库的项目装上 skill 后零负担（静默退化为原 SOP）

**Non-Goals:**

- 不引入跨项目通用规范库（每个项目自有库）
- 不在首期实现 decision spec（跨模式铁律），只留 ID 命名空间
- 不引入向量检索或外部依赖（一切基于 Markdown + frontmatter）
- 不改变 Phase 2/3/4 的核心契约（v2 Markdown 格式、Figma 引擎调用）
- 不假设用户的项目目录结构（除约定的 `.interaction-sop/` 入口外）

## Decisions

### D1. 模式库由 schema + 项目数据两层组成

**选择**：skill 仓库只携带 schema 与协议；项目仓库自带 `.interaction-sop/` 目录。

**为什么**：skill 通过 git 分发到任意项目，项目术语、领域、案例完全不同。若把模式库内容塞进 skill，对其他项目毫无意义。模式格式必须共享（保证 schema 演进可控），内容必须项目本地化。

**替代方案**：
- 让 skill 携带"通用模式起步包" → 否决，模式必须有真实案例支撑，凭空写的"通用模式"会污染所有项目
- 用全局配置中心服务 → 否决，引入新依赖，破坏"一句话主义"

### D2. 模式（Pattern）按"分层信息"组织，而非平铺字段

**选择**：每条模式分四段：核心交互逻辑 / 必复用核心骨架 / 通常需要重定的参数 / 容易需要重新决策的地方。

**为什么**：这四段对应 Agent 在 Phase 0 输出咨询时的四种话术（讲一遍逻辑 / 这部分基本可复用 / 这部分要单独定 / 我留意到的差异点）。如果只有平铺字段，Agent 无法判断"哪些是骨架不可改、哪些是参数可调"，会把所有点都当"可能要改"，用户每次都要回答一堆，没省到事。

**替代方案**：
- 单条原子决策（decision-only）→ 否决，颗粒度过细，新需求会命中几十条原子规则，反而问爆用户
- 自由 Markdown 段落 → 否决，Agent 无法稳定解析，跨项目格式漂移
- 增加"硬骨架/软骨架"分级 → 否决，三层结构已覆盖该梯度，多一层只增加复杂度

### D3. Frontmatter 承担检索，正文承担咨询

**选择**：模式条目的 frontmatter 字段堆得较满（id / status / matching_signals / project_terms / case_files / glossary 关联），正文用固定标题结构（H1/H2 严格）。

**为什么**：Phase 0 检索阶段只读所有模式的 frontmatter（30 条约 12KB，可一次塞 prompt），命中后再读正文展开。这样库长到 100 条也不爆 prompt。Agent 友好优先（不要求人手写），可以用结构化字段。

**关键字段**：
- `matching_signals.intent_keywords / ui_signals / anti_signals`：anti 加权惩罚（×2），降低误配率
- `project_terms` + `index.md` 的 `project_glossary`：项目术语别名归一，提升召回精度
- `case_files`（必填 ≥1）：物理上杜绝"凭空造规则"
- `schema_version`（全套统一）：演进时迁移协议的唯一抓手

### D4. Phase 0 输出嵌入 Phase 1 第一回合，不单独走一个回合

**选择**：Agent 内部完成 8 步检索流程，输出与原 Phase 1 第一回合的"复述+提问"融合为一段。

**为什么**：单独走 Phase 0 回合（"我先查查...命中 P-001，是否套用？"）会增加用户等待感与回合数。融合后用户感受到的是"Agent 一开口就已经看过老案例"。

**输出模板要求**：
- 必有"复述理解"段
- 命中时插入"看到相关历史"段（口语化讲完整流程 + 必复用 / 待重定 / 留意差异 三类标记）
- 有 ⚠️ 冲突时强制插入"与项目规范的潜在冲突"段（列两种可能 / 不替策划下结论）
- 末尾固定一句"如果方向不对告诉我"（显式留反驳通道）

### D5. 跨 Phase 注入通过"采用契约"实现，会话级不持久化

**选择**：Phase 1 内部维护 `adopted_patterns / confirmed_facts / deviations_pending / unresolved_conflicts / pending_questions` 状态。命中且采用后，骨架决策自动注入 `confirmed_facts`，跨 Phase 2/3/4 持续生效。

**为什么**：
- 不落盘：跨会话恢复反而引入"采用契约过期"问题；用户重答一次"采用 P-001"成本极低
- 撤销机制：用户在任何时候说"不要用 P-001 了" → Agent 识别 → 状态回滚 → 已落盘的 Markdown 提议重写

### D6. 增量提取按"风险/可逆性"分级自动化

**选择**：

| 操作类型 | 处理方式 |
|---|---|
| 数据追加型（case_files / glossary / 一次性偏离） | 全自动 + maintenance.log |
| 元数据修订型（matching_signals 补充） | 全自动 + maintenance.log |
| 立新模式 | 草案直接落盘 + 一句话提示 + 随时 override（方案 d） |
| 结构性变更（拆分/合并/废弃/改核心骨架） | Agent 建议写 maintenance-suggestions.md，必须用户 review 才执行 |

**为什么**：
- "全 review" → 用户疲劳 → 库腐烂
- "全自动" → 累积误差 → 黑箱化 → 错误放大
- 分级是唯一兼顾安全与效率的方式
- 沉默通过用方案 d（直接写盘 + 用户随时 override + maintenance.log 可追溯）：Agent 无法后台等待 / 用户不一定常打开仓库 / 时间窗口不靠谱

### D7. Agent 不可替策划判定"对错"

**选择**：当 (需求 vs 模式) 矛盾时，Agent 必须显式暴露冲突 + 提供"有意打破 / 顺手写错"两种可能 + 等待用户拍板。

**为什么**：策划文档可能带有自创交互设计但与项目规范不符。Agent 自动选边（"按规范来"或"按策划写的"）都会损害用户的项目治理权。Agent 的角色是"看见冲突的人"，不是"决定对错的人"。

**硬约束**：未决冲突存在时禁止进入 Phase 2，即使用户说"直接写完整 Markdown"也要先定冲突。

### D8. 模式成熟度通过 case_files 数量隐式表达

**选择**：不引入显式"成熟度"字段，用 `case_files` 长度区分种子模式（=1）/ 初步成熟（=2）/ 稳定模式（≥3）。Agent 在 Phase 0 输出咨询时按成熟度调整措辞强度。

**为什么**：避免新增字段；自然反映模式被引用频次；用户读输出措辞即可感知模式可信度。

### D9. Glossary 由 Agent 在提取时维护

**选择**：在 `index.md` frontmatter 中维护 `project_glossary`，记录术语别名映射。Agent 提取新模式时扫 `project_terms` 字段，与 glossary 比对，发现新词或别名时提议合并。

**为什么**：项目术语随时间漂移（"小兵" / "单位" / "卡牌" / "部从" 同一概念多名）。Phase 0 通过 glossary 把用户需求中的别名归一，命中率显著上升。

## Risks / Trade-offs

- **[累积误差]**：增量自动操作单次准确率 95%，多次后误差累积 → 通过 maintenance.log + 用户随时回滚 + 结构性变更必 review 限制爆炸半径
- **[Agent 黑箱化]**：自动操作让用户不清楚库变化原因 → maintenance.log 强制写"为什么这么判断"
- **[误配 vs 漏配]**：matching_signals 阈值设高会漏配、设低会误配 → anti_signals 加权惩罚 ×2 + 协议规定 Agent 自适应调整阈值（漏配走原 SOP 无伤；误配让用户被错误建议诱导）
- **[策划权威性争议]**：Agent 暴露冲突时用户可能没有项目规范的最终决策权 → 输出措辞中性，提供两种可能但不施压；用户可走"全盘推翻"路径
- **[Schema 演进迁移成本]**：首期 schema 不可能完美 → 引入 `schema_version`，未来加迁移协议（首期不实现，靠 schema_version 兼容性保留接口）
- **[冷启动用户负担]**：30 个文档批量提取 review 量大 → 分批 5 个一组 + 支持中途暂停（跨日重启时 Agent 重扫，跳过已建模式）
- **[模式拆分错误回滚成本高]**：拆分后 case_files 分配错会污染检索 → 结构性变更必须 review；Agent 只能写建议，不能自动执行
- **[未命中静默退化的用户体验]**：检索 0 命中 → 静默走原 SOP（不提"查过但没找到"） → 用户感知不到检索环节做了功课 → 接受，否则每次都说"查了没找到"反而浪费用户阅读时间
- **[跨项目 schema 漂移]**：项目可能自行扩展字段 → schema 文档明确"未识别字段 Agent 应忽略而非报错"，保证向后兼容

## Migration Plan

本次改造对未启用模式库的项目零影响。启用模式库的项目按以下顺序：

1. skill 仓库发布新版本（含 schema、phase0/5、phase1 改造）
2. 项目侧首次使用新版 SOP 时，Agent 检测无 `.interaction-sop/` 目录，提议"看到你有 N 个交互文档，要建库吗？跳过也行"
3. 用户选择建库 → 走 Phase 5 冷启动流程
4. 用户选择跳过 → SOP 行为与旧版完全一致，可任何时候触发"扫文档建库"补建
5. 建库后下一个需求自然走 Phase 0 检索

**回退策略**：用户可随时删除 `.interaction-sop/` 目录，SOP 自动退化为原版；或用 maintenance.log 按时间窗口回滚增量操作。

## Open Questions

- Phase 5 冷启动的批量尺寸是否应可配置（默认 5 个/批）？首期建议固定 5
- 跨模式术语的标准化粒度（"hover" vs "鼠标悬停"）由谁定？首期由 Agent 提议、用户 review，不立项目级强制术语表
- 长期是否需要"决策 spec（D-XXX）"作为跨模式铁律的承载？观察 6 个月模式库使用情况后决定，schema_version 可向上兼容
- maintenance.log 是否需要轮转 / 归档？首期不做，单文件足够；规模大后再加
