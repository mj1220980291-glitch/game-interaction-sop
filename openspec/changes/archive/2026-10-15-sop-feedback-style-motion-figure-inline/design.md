## Context

`引擎开发反馈.md` 把设计同学手改后的 Figma 与引擎渲染稿逐条比对，归纳出 6 类问题。其中「文风 / 废话 / 动效 / 配图位置」四类根因在 LLM 转写阶段（Phase 2），可只改 skill 文档修复；「配图框尺寸、裁剪、增量渲染、超时、错误信息、状态块样式」根因在 `packages/figma-mcp-server`，本次不处理。

现行相关规则：
- `markdown-v2-spec.md` W3：`配图：` 是簇内最后一条 bullet
- `phase2-markdown.md` 拆分启发法第 6 步：需要配图则在簇最后加一条
- `phase2-markdown.md` 自检可选项：bullets ≥ 6 条考虑 `####`
- 现行规范禁止"待确认"类标记与 `## 待确认问题汇总` 段

## Goals / Non-Goals

**Goals:**
- LLM 产出的 bullet 只写设计稿看不出来的信息增量，簇 bullet 数落在 3–6 条
- 动效 bullet 统一三段式、同类合并、覆盖显隐
- `配图：` 位置即语义，原位插入、一簇多张
- skill 文档与主 spec 双向一致

**Non-Goals:**
- 不改 parser / render（不新增校验码，不改配图渲染）
- 不开文末「待补充」区
- 不引入 `- 状态｜默认：` 状态块语法（依赖引擎样式支持，归引擎 change）
- 不做自动语义相似度去重（反馈建议的"相似度阈值"属引擎/工具能力，本次仅作为 LLM 自检项）

## Decisions

### D1：信息增量判据用"看图能否得出"一问
LLM 对每条 bullet 自问："设计师/程序看主图或配图能不能直接得出这句？"能 → 删。比列关键词黑名单更稳；配合正反例（取自反馈原文）落地。
- 备选：维护"低价值句"关键词表（位于/固定 N 行/占位文案）——误杀率高，否决。

### D2：参数/数值不逐条列举，也不开待补充区
用户决策：维持"无待确认标记"。参数类收束为一句"具体参数策划配表即可"，属于明确的分工陈述而非开放问题，不违反现行卫生项。

### D3：动效节奏由 LLM 给建议值
"节奏由策划配置 / 形式待定"等同待确认标记，禁止。LLM 按交互常识给出曲线/节奏建议（减速收尾、弹性、闪烁频率等），与 T5 UI 反馈补全同属"设计师职责内主动拍板"。

### D4：`####` 降为最后手段
反馈显示 `####` 在大文档里易触发渲染超时，且 bullet 过多本身是混入可见信息的信号。改为：>6 条先按 T6/T7 删减合并，仍 >6 且可明确分类时才用 `####`。spec 中 `####` 语法本身不变。

### D5：配图原位规则先于引擎落地
Markdown 是真源，先把位置语义定下来；引擎当前只渲染首个 `配图：` 描述到簇末，属已知差距。
- 备选：等引擎改完再一起改——会让本次文风改动被阻塞，否决。

## Risks / Trade-offs

- [引擎只渲染首个配图描述，其余描述在 Figma 丢失] → proposal/Phase 4 话术注明；设计师以 Markdown 为准手贴图；引擎 change 跟进
- [过度删减导致程序缺信息] → T6 只删"看图可得"的静态信息，行为/边界/配表/动效曲线一律保留
- [LLM 给的动效节奏与美术预期不符] → 属正常审稿修改范围，比空句"待定"更易推进
