## 上下文

分享对象是**没跑过这套 SOP 的设计团队**。他们的第一次接触顺序固定为：

```
拿仓库 → 装依赖/编译 → 配 MCP → 开插件 → 跑 demo → 自己写第一篇
```

过去两周踩的坑全部落在这条链上，而不是渲染算法里：

| 环节 | 曾踩的坑 | 现在状态 |
|---|---|---|
| 装依赖 | 机器 PATH 无 node/npm | 文档给绝对路径（`AGENTS.md` 已有约束） |
| 配 MCP | 输出 `command: "node"` → 宿主 `spawn ENOENT` | **本 change 修** |
| 模板包 | 项目包被 gitignore、用户包在仓库外 → 换机器必丢 | 0.4.4 起随引擎分发基线包 |
| 模板包内容 | 只挑了官方 1.14，且缺 4 个原值；蛋仔根本没有 | **本 change 补** |
| 观感异常 | 缺底色时静默白底 | 0.4.7 起两条软告警 |
| 抖动 | 10s 连接超时连撞两次 | 0.4.8 起 3 次 + 递增退避 |

所以本 change 的目标不是加功能，是**把链路上的「静默失败」逐个变成「显式可用」**。

### D1｜安装片段写绝对路径，不写 `node`

`process.execPath` 是唯一在「运行安装脚本的这台机器」上保证正确的路径。宿主（CodeMaker / Claude / Cursor / Cline）拉起 MCP 用的是**宿主的 PATH**，不是 shell 的 PATH，两者不一致是常态。

代价：仓库挪位置要重新生成片段。可接受——重生成只需一条命令，而「连不上」排查要一整晚。

### D2｜两套基线包都要「完整」，且必须重编而非手写

- `default.json` = 官方 1.14：补 `placeholder{fill,stroke}` / `bubbleGrid` / `docPadding` / `footerGap`
- `蛋仔派对.json` = 蛋仔：整套重编（当前机器没有该包）

为什么不能手写：`componentKey` 是发布快照的产物，手抄必错；`bubbleGrid` 是原稿标号点位，只能从源稿量。

产出流程固定：`phase=compile`（`staged.chapter` = 源稿章节）→ 人工发布 → `phase=verify` → `audit_template_pack` 体检 → 覆盖入库。

### D3｜给「库已发布」场景补一条采集路

其他团队大概率是「我们已经有组件库了，不想整轮重编」。`captureGeometryFromKeys` 目前不传 `sectionSourceId` / `sourceRootId` / `badgeSourceId`（其中 `sourceBackend` 是死参数），导致这条路径永远采不到 `sectionShell`，只能出「没有章节外壳」的残包。

修法：三个参数透传；没有原稿 id 时在 `gaps` 里写「缺原稿章节 id，章节底色/黑边采不到，请走 compile」。

### D6｜共享桥诊断必须基于最近往返（2026-11-13）

现场父链证明 9223 的 console child 属于 worker 7908；worker 将同一 client 同时交给 proxy 与 backend。内部 probe 已读到沙盒文件名，故不存在已证实的隔离 client。`get_skill_requirements` 只读启动缓存，启动时插件尚未重连产生的 false 一直未刷新，误导为持续断连。历史 verify 错误来自执行 `importComponentByKeyAsync` 的脚本，不能仅凭其 “Unable to establish connection to Figma” 文案认定桥无客户端；导入网络/库状态的具体成因尚未证实。

最小修复：backend 每次成功 execute 更新最近往返；明确 Cannot connect 桥错误才置 false，插件脚本错误不得抹掉已有成功证据。healthCheck 必须收到 `return 1` 的真实结果才成功。MCP isError 与无 `_mcp` 的 success/error envelope 均须按失败处理，不把错误对象当节点或健康结果。proxy 保持原样透传，同一 client、多文件 withFileKey 绑定不变。回归覆盖启动 false 后内部恢复、脚本连接措辞不误报桥断连、MCP 错误 envelope、同 client 外部/内部及并发多文件。无新工具、无自动重连/杀进程/导入重试策略扩展；真实 verify/render 留主代理验收。

### D7｜verify 阶段错误须可定位（2026-11-13 deeper focused）

四原子在沙盒独立 remote import 成功不证明 verify 全链通过。verify 依次执行四 key 冒烟、库文件章节实例化与几何读取、源文件章节/标号读取、文档留白读取；职能 keys 不参与此阶段。冒烟会聚合失败，故无聚合前缀的历史 INTERNAL_ERROR 更指向后续阶段，但尚无现场 stage 证据。

最小诊断：verify 添加 smoke / geometry / spacing 阶段前缀；backend execute 错误附绑定 fileKey，import/instantiate 另附操作、key、脚本内 import/serialize/create/parent 阶段。原始错误与 code 保留，不输出脚本、环境或 token。实例化错误不得无条件宣称 key 失效；仅明确组件不存在错误保留 stale 分类。创建实例后脚本失败须清理本轮实例；几何采集后的清理失败须记录 gap，不能静默。不新增导入循环/重试，不改绑定或发布状态，不把 REST token 过期当作插件导入失败原因。回归实际执行生成脚本并验证定位与清理；真机须新代码加载后只做一次 verify。

### D9｜verify 冒烟要有可观测性与桥级短路（2026-11-16）

只读复核 2026-11-16 两轮 verify 后，能确认的只有：整个服务在 10:54:05 被换（supervisor+worker+bridge），不是本地动作（无 terminal/edit、dist 未变、系统无崩溃/休眠）；dispatch 不等就绪（bridge 10:54:07、figma-console 10:54:09、import 10:54:09.9、插件 10:54:13.5 才连）；两次错误都是 `Cannot connect to Figma Desktop.`，带我们的 `[importComponentByKey … file=…]` 前缀、无插件侧 `stage=`。**未确认**：supervisor 为何退出（宿主不落 MCP 生命周期日志）；两次 verify 内部那 ~64s 花在哪。**已推翻**：figma-console-mcp 1.46 的 no-client 是快路径（`getDesktopConnector()` 在 `isClientConnected()` 为 false 时立即抛错，`websocket-connector.js:50-53`），所以「每部件 ~16s 等回连」不成立；「插件在 import 期间沉默」也只能降级为「figma-console 判定没有活客户端」，插件忙/陈旧 socket/被 30s 心跳 terminate 三者当前分不开。另：现场插件 `1.39.0` ≠ 打包 `1.41.5`。

决策（只加观测与短路，不改传输语义）：

1. **冒烟逐部件记明细**：每个部件记 `{part, key, startedAt, elapsedMs, errorKind}`，失败信息里附人读摘要与 `details`，不再只给一句聚合。`errorKind` 分 `no-client` / `no-reply` / `busy` / `not-published` / `other`；分类只看原始错误文本与已有 `V2_BRIDGE_NO_REPLY`，不新增探测。
2. **桥级失败短路**：`no-client` / `no-reply` / `busy` 出现即停，未尝试的部件要标明「未尝试」，不冒充四键都不可用；`not-published` 继续聚合（一次列全缺哪些更有用）。错误 code 仍是 `V2_COMPILE_VERIFY_UNAVAILABLE`。
3. **失败信息带桥快照**：`port/preferredPort/fallback/holderPid/pluginConnected/lastRoundtripMs/checkedAt/workerPid/supervisorPid`，取自已有 `bridgeState`，不发额外往返。
4. **冒烟前一次有界就绪探活**（`verify.bridge` 阶段）：复用 backend `healthCheck`（`return 1`，5s 插件超时），失败直接以桥级错误结束，不进入四键循环。成功率高的路径只多一次毫秒级往返；不等待重连、不循环重试。
5. **worker 启动留痕**：追加一行 JSON 到 `~/.game-interaction-sop/worker-lifecycle.log`（pid、supervisorPid、startedAt、engineVersion、探活结论）。宿主不收 stderr，重启史只能靠自留痕；写失败不影响启动。
6. 不做：不加导入循环/重试、不延长任何超时、不开额外 worker、不改绑定/发布状态/配置/凭据、不把版本漂移自动修复。

### D10｜组件变体模式下，模板自带的职能行按 md 角色取舍（2026-11-16）

真机验收（渲染 root `182:625`）发现：2 章 3 簇里每簇都显示三条职能行（程序 / GUI / CCS），带模板占位正文「XX职能正文占位：…」，与 md 实际标注的 `@GUI`、`@策划 @动效`、`@程序 @拼接` 不符；同步因这 9 个实例固定产生 9 条 conflicts，「零变更零冲突」无法达成。

三个模板的母版实况（只读扫描）：官方 1.14 的簇里只有 1 个叫 `职能标记` 的空 FRAME（1231×70，无角色后缀、无文字）；蛋仔是 `inline-suffix` 且簇里没有任何职能节点；燕云簇里预置了 `职能标记=#程序/#GUI/#拼接` 三个可见 INSTANCE，各自带占位正文。代码侧 `render/parts/index.ts` 的 `component-variant` 分支只有注释、没有清理，只有非组件变体才 `deleteMatching(isRoleFrameNode)`。所以这不是「燕云模板坏了」，而是「模板预置了职能载体 + 渲染器从不消费」的组合，当前只有燕云同时满足；官方 1.14 的空框同样没被消费，只是没有文字、不产生冲突，看不出来。

决策：

1. `component-variant` 模式下，簇里名字为 `<variantPrefix><角色>` 的载体按本簇 `roles` 取舍：标注了的保留并显示，没标注的 `visible=false`。**用隐藏不用删除**——删掉会让本来就按行排的版面塌一截，隐藏保版面且可回退。
2. 只认「带角色后缀」的载体；纯 `<variantPrefix>` 容器（官方 1.14 那种）不动，它是实例的落点。
3. 标注角色的正文以 md 为准：该模式 md 只写角色名、不带正文，所以把载体里模板的占位正文清空；若 md 用 `@角色：正文` 的写法（由 fillCluster 另建实例承载正文），则把模板载体隐藏，避免同一角色出现两行。
4. 隐藏/清空失败只记一条软警告（`V2_W_ROLE_CARRIER_LEFT`），不让整篇渲染失败。
5. 与 D0/8.9c「清洗时保护承载正文/标题的标签框」不冲突：那条约束的是**清洗旧稿**，这里约束的是**渲染产物**。
