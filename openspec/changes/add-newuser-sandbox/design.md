## 上下文

「新用户能不能装起来」这件事，过去靠人记、靠临时手测。要能反复验证，需要三件事同时成立：

1. **环境可重建**：干净目录、空用户配置、可控的 PATH
2. **路径可复现**：既能模拟真实拉仓库，也能模拟「我改完代码还没推」
3. **结论可比较**：每次跑完产出一份结构化的报告，改动能 diff 出差异

## 决策

### D1｜脚本放在仓库里，不放在沙盒里

沙盒是**被测物**，脚本是**测量工具**。脚本从原始仓库运行、操作沙盒目录，这样脚本本身不会因为被测代码改坏而失效。

### D2｜三种隔离，分别对应三类故障

| 隔离 | 模拟什么 | 能抓到什么 |
|---|---|---|
| 独立 `HOME` / `USERPROFILE` | 新机器、无历史配置 | 依赖 `~/.game-interaction-sop` 才能跑的东西（模板包、roleBlock、supervisor 锁） |
| 独立 `TEMP` | 无残留桥信息 | 端口残留 / 旧 lock 文件导致的假死 |
| `PATH` 不含 node | 别人的机器 | `spawn ENOENT`、「MCP 面板一直连」 |

### D3｜默认不连 Figma

渲染需要 Figma + 插件 + 库权限，三者在新用户场景下**必然缺一**。默认只跑「不需要 Figma 也能验证」的 80%：

- 装依赖 / 编译
- 安装片段是否正确（绝对路径、文件真实存在）
- 引擎能否起来、原生工具是否齐全
- 空 HOME 下能否命中**仓库自带**的基线包
- 书写契约能否从包重建

`--with-figma` 才追加渲染步骤，失败不算沙盒失败（单独标注 `skipped`）。

### D4｜报告要能 diff

`report.json` 里每步固定字段：`id / status / durationMs / firstError / assertions[]`。两次运行只比较 `status` 与 `firstError`，人读的 `report.md` 同步生成。

时间只在同一台机器上有意义，因此报告里**记录但不比较**。

### D5｜`no-node` 模式只验证「文档说的是真的」

PATH 里没有 node 时，`npm` 本身就跑不起来（`npm.cmd` 内部要 `node`）。所以该模式不跑完整安装，只验证三句话：

1. `node -v` 失败
2. `<node 绝对路径> -v` 成功
3. 把 node 目录加回 `PATH` 后 `npm -v` 恢复

对应 `docs/onboarding.md` 里「全部用绝对路径」的说明。

## 风险

| 风险 | 缓解 |
|---|---|
| 脚本误删用户目录 | 只删 `--root` 之下的内容；`--root` 必须是空目录或带标记文件 |
| `npm install` 很慢（workspaces） | 单步 15 分钟上限；报告标注耗时，便于判断是不是环境问题 |
| 沙盒里改脚本导致自证 | 脚本从原始仓库运行，被测代码只在沙盒 |
