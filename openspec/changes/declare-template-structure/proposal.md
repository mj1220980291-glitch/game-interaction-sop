## Why

2026-11-18 用燕云模板做真机对比（渲染稿 `201:4247` vs 原稿 `201:5487`）暴露出一类系统性问题：**引擎的文档模型只有 4 个部件（顶部 / 章节 / 簇 / 结尾）**，渲染只认一套写死的槽位名（`#Name`、`#Title_Main`、`正文/规则`、`配图`、`气泡`、`主图占位`…），以及一套写死的组件形态（职能 = `职能标记=` 变体集，标号 = `气泡` 容器 + 母版）。结果是：

- 燕云原稿顶部的 **跟进人 / 修订记录 / 审核情况 / 需求概述** 4 块不属于任何部件 → 编译期就被丢掉，渲染完全不知道它们存在（且不报警）
- 燕云的角色标签实际是 `职位=GUI注意` 组件集（标签文案 `GUI / VX / 程序`），标号是标题行里的 `序号` 组件实例 → 引擎只能用 `职能标记=` 与 `气泡` 母版去凑，样式、文案、位置全不对
- 正文列宽按 `chapterWidth` 推，源稿列宽不同就偏

根因不是某个分支写错，而是**模板结构知识只存在于引擎代码里**：模板必须被编译改造成引擎认得的骨架（「换皮式接入」），契约外的结构静默消失。每接一个新项目模板都要人工改造并承担漏块风险。

## What Changes

- pack 新增**结构声明**（`layout.blocks`）：模板自己声明「有哪些块、每块用什么部件、槽位怎么映射、重复策略、角色/标号的组件形态」。声明由编译期生成草案、人工确认后写回 pack。
- **声明是唯一运行时路径**：渲染、同步对账、编译校验都读声明；没有声明的老 pack 由「默认声明生成器」（以现有 8 项能力为输入）生成等价声明后走同一条路径，永久兼容。
- 渲染从「按名字找节点」改为「按声明遍历块」：`text` / `list` / `table` / `repeat` 四类块 + 条目级渲染器（文本、配图、角色实例）。
- 对账标识从「名字路径」改为「`blockId/slotId + 行序`」，老文档 stamp 通过归一化层兼容。
- md 契约新增三段可选内容：`## 需求概述`、`## 修订记录`（Markdown 表格）、`## 审核情况`（键值行），给顶部新增块提供数据源。
- 角色标签与标号的组件形态直接写进声明（角色 → 变体 key 映射；标号 `container` / `instance` / `none`）；8 项能力表**降级为默认声明生成器的输入**，渲染期不再直接读能力枚举。

## Capabilities

### New Capabilities

- `template-structure-declaration`：模板结构声明（块 / 槽位 / 重复 / 组件形态）的 schema、默认声明生成、声明驱动的渲染与对账、单一告警源。

### Modified Capabilities

- `template-contract`：pack 增加 `layout` 字段与 `schema_version: 2`；能力表字段保留但语义降级为「默认声明输入」。
- `markdown-v2-contract`：新增 `需求概述 / 修订记录 / 审核情况` 三段可选内容与对应解析规则。
- `template-render`：渲染入口由「按槽位名填充」改为「按声明填充」；未声明的节点不再被写入。
- `render-reconcile`：对账条目标识改为声明 id；老 stamp 归一化兼容。

## Impact

- 新增：`src/v2/template/layout-schema.ts`（声明类型与校验）、`src/v2/template/default-layout.ts`（能力表 → 默认声明）、`src/v2/render/blocks/*`（声明驱动渲染）、`src/v2/reconcile/layout-identity.ts`（对账标识归一化）
- 改动：`parser.ts`（三段新内容）、`compile/md-contract.ts`（新段文案）、`compile/index.ts`（生成并写回声明 + 声明校验）、`render.ts` / `render/parts/index.ts`（按声明渲染，移除按名查找）、`reconcile/*`（标识归一化）、`capability-contract.ts`（降级为生成器输入）
- 兼容：`schema_version: 1` 的 pack 无限期可加载；老文档不重渲也能继续同步
- 不在范围：样式/几何的声明化（声明只管结构与槽位）、新增设计系统能力、模板视觉调整
- 开发在**新对话**进行；本 change 只作为 spec 与任务清单
